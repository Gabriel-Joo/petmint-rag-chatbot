### 1. 이전 시도에서 확인한 것

이 프로젝트에서 파인튜닝을 시도한 적이 있다. 옛 청크·옛 FAQ로 한 것이라 지금 데이터와 연결이 없어 별개 작업으로 보지만, 거기서 확인한 세 가지는 이번 설계의 근거가 됐다.

#### 1-1. 지시와 데이터가 모순이면 지시가 무시된다

```
system 프롬프트:  "발췌에 있는 내용만 근거로 답하라"
학습 데이터:      발췌 없음. question → answer
```

발췌를 주지 않으면서 "발췌만 보라"고 지시한 셈이다. 모델은 **사실을 가중치에 외우는 법**을 배웠고, 테스트에서 원문에 없는 "특별약관은 5영업일 이내"를 단정했다.

"말투만 배우고 사실은 RAG가 담당한다"는 역할 분담과 정반대 결과다.

#### 1-2. 고정 패딩으로 계산의 2/3가 낭비됐다

모든 샘플을 768토큰으로 패딩했는데 실제 길이는 평균 250 정도였다. 동적 패딩과 `group_by_length`로 바꾸면 그만큼이 줄어든다.

#### 1-3. loss를 전체에 걸면 안 된다

system 프롬프트와 질문에도 loss가 걸려 있었다. 발췌를 넣고 그대로 두면 **loss 대부분이 약관 원문을 외우는 데** 쓰인다.

### 2. 학습 데이터 형식 — 왜 발췌를 넣는가

세 가지를 비교했다.

|  | A. 발췌 없음 | B. 정답 발췌 | C. 정답 + 방해 발췌 + 답 없음 |
| --- | --- | --- | --- |
| 모델이 배우는 것 | 사실을 외움 | 읽고 옮기기 | 읽기 + 관계없는 발췌 무시 + "확인 필요"라고 하기 |
| 샘플당 토큰(추정) | 약 250 | 약 850 | 약 1,500 |
| 학습 시간(추정) | 약 30분 | 약 1.6시간 | 약 3~3.5시간 |

**C를 선택했다.** 이유는 실제 RAG 상황과 같기 때문이다.

추론할 때 검색은 top_k개를 가져오는데 그중 일부는 질문과 관련이 없다. 정답 발췌만 주고 학습하면(B) 모델은 "주어진 건 전부 관련 있다"고 배운다. 방해 발췌를 섞어야 **무시하는 법**을 배운다.

"답 없음" 샘플은 검색이 실패했을 때를 위한 것이다. 발췌에 답이 없으면 지어내지 말고 "확인이 필요하다"고 말하도록 가르친다.

**구성**: 정답+방해 70% / 정답만 20% / 답 없음 10%

> 학습 시간이 생각보다 덜 늘어나는 이유: 1-2의 고정 패딩을 고치면 그만큼이 상쇄된다.

### 3. 학습과 추론의 형식을 코드로 묶는다

가장 중요한 설계 결정이다. 형식이 어긋나면 파인튜닝 효과가 사라지는데, 두 곳에 따로 쓰면 어긋나기 쉽다.

`data/prompts.py` 하나를 **07번 학습, 09번 앱 추론, 08번 평가가 함께 import**한다.

```

     ↓ 같은 모양

```

출력 형식:

```
[약관 발췌]
[발췌 1] 펫퍼민트 반려견 통원의료비Ⅱ보장 특별약관 제1조(보험금의 지급사유) 고급형

  [참조] 반려동물 비용손해 관련 특별약관 일반조항 제15조(재가입) 제6항

[질문]
```

**길이 예산을 넘을 때 뭘 빼는지도 한 곳에서 정한다.** 아래쪽 발췌의 참조부터 빼고, 그다음 아래쪽 발췌를 통째로 뺀다. 학습 시 정답 발췌는 `protected`로 지정해 참조까지 보존한다.

### 4. 고객 정보를 프롬프트에 넣지 않는다

09번 UI는 고객을 조회해 가입 정보(등급·유형·자기부담금·부담보)를 들고 있다. 그런데 그걸 모델에게 주지 않는다.

**이유 ①: 검색 필터가 이미 처리한다**

```
넣는 방식    "이 고객은 고급형Ⅱ입니다. [발췌: 통원Ⅰ·Ⅱ·Ⅲ 전부] 질문: 수술비?"
             → 모델이 "고급형Ⅱ니까 Ⅱ를 봐야지"를 추론해야 함

지금 설계    검색이 이미 Ⅱ·고급형만 가져옴
             "[발췌: 통원Ⅱ 고급형] 질문: 수술비?"
             → 모델은 주어진 발췌만 읽으면 됨
```

01번부터 지켜온 **"모델이 추론할 필요를 없앤다"** 원칙을 그대로 이은 것이다.

**이유 ②: 학습에 없던 블록은 추론 때 쓸 수 없다**

추론 때만 넣는 선택지는 없다. 넣으려면 학습 데이터 전체에 고객 정보 블록을 붙여 다시 만들어야 한다.

**이유 ③: 7B가 가장 많이 틀리는 유형이다**

부담보("슬개골 탈구는 보장 제외")나 면책기간("가입 후 30일 이내 질병은 제외") 판단은 예외·단서 추론이다. 06번 심판 결과를 보면 모델이 가장 많이 틀리는 영역이다.

```
incomplete (핵심 조건 누락)  28%
reversal (결론 뒤집기)       18%
clause_mix (예외·단서 섞기)  17%
```

**대신 코드가 처리한다**

| 정보 | 처리하는 곳 |
| --- | --- |
| 등급·유형 | 검색 필터 (SearchScope) |
| 자기부담금 | 계산 카드 (limit_table.calculate_payout) |
| 부담보 | 코드가 질문과 대조해 경고 배너 |
| 가입일 | 코드가 경과일을 계산해 카드에 표시 |

`build_messages(customer=...)`에 값을 넘기면 `NotImplementedError`가 난다. 결정을 코드에 박아, 나중에 흔들리지 않게 했다.

### 5. 계산을 프롬프트에 넣지 않는다

05번에서 측정한 결과다.

| 조건 | 계산 오류율 | 파싱 실패 |
| --- | --- | --- |
| 아무 조치 없음 | 35% | 2/48 |
| "직접 계산하지 말 것" 지시만 | 16% | 1/48 |
| 지시 + 코드가 계산한 표를 프롬프트에 | 21% | 15/48 |

**코드 계산표를 넣으니 오류가 오히려 올랐다**(16% → 21%). 그리고 프롬프트가 길어지면서 JSON 출력이 31% 깨졌다.

그래서 계산은 **답변 옆 카드로 분리**한다. `limit_table.calculate_payout` 결과를 UI가 따로 보여주고, 모델은 계산에 손대지 않는다. "계산 카드를 참고하세요" 같은 안내 문장도 모델이 아니라 UI가 붙인다.

이렇게 하면 **학습 데이터를 건드릴 필요가 없다.** 프롬프트에 계산값을 넣기로 하면 계산형 QA 289건 이상을 다시 만들어야 하고, 한도표가 바뀔 때마다 재학습해야 한다.

### 6. 대화 이력도 넣지 않는다 — 멀티턴은 백엔드가 처리

"그럼 입원은요?" 같은 후속 질문은 그대로는 검색이 안 된다. 그런데 **대화 이력을 프롬프트에 넣는 방식은 쓰지 않는다.**

학습 데이터는 전부 `[system, user]` 2턴이다. 이력을 넣으면 학습에 없던 형식이 되고 재학습이 필요하다.

**대신 백엔드에서 처리한다**

| 방법 | 내용 |
| --- | --- |
| 질문 재작성 | 이력 + 후속 질문 → 독립 질문. 모델에는 완성된 질문 하나만 간다 |
| 앞 턴 발췌 이월 | 직전 턴의 상위 발췌를 이번 발췌 목록에 추가. 형식이 그대로 ExcerptItem 목록이라 안 깨진다 |

두 번째가 특히 깔끔하다. **2절의 C안이 "여러 발췌 중 관련 있는 것만 쓰기"를 가르치므로 오히려 유리하다.**

**재작성기는 베이스 모델을 쓴다.** 파인튜닝 모델은 "발췌를 읽고 상담 말투로 답하기" 하나만 배우므로, 재작성을 시키면 질문을 다시 쓰지 않고 답을 해버릴 가능성이 크다(추정, 미측정).

> 부수 효과: 학습 질문은 FAQ 질문이라 완결된 문장이다(중앙 53자). 상담원이 실제로 칠 짧은 질문("슬개골 돼요?")도 재작성기가 다듬으면 학습 때와 같은 꼴이 된다. 멀티턴이 아니어도 얻는 이득이다.
> 

**"더 짧게", "고객에게 말하듯이 다시" 같은 고쳐쓰기**는 검색 질의 문제가 아니라 직전 답변을 입력으로 받는 다른 작업이다. UI 버튼으로 받아 베이스 모델에 넘긴다. 약관 사실은 이미 직전 답변 안에 있으므로 베이스 모델로도 된다.

`build_messages(history=...)`도 `NotImplementedError`를 낸다.

### 8. 학습 실행

#### 8-1. 메모리 문제 — 쓰지 않을 logits를 만들고 있었다

첫 실행에서 step 2를 넘지 못하고 멈췄다.

```
[W] expandable_segments: memory mapping failed with OOM on device 0
    while trying to map 20971520 bytes (free: 7864320, total: 16608133120)
```

2분 동안 step 2에 머물렀고 free 메모리가 7.8MB → 3.6MB로 줄었다. GPU에 다른 프로세스는 없었다.

**원인 ① 설정 실수**: 사전 점검(최대 할당 14.1GiB / 예약 15.1GiB)은 `expandable_segments` 없이 측정했는데, 그 뒤에 이 설정을 테스트 없이 넣었다. 여유가 0.4GiB뿐이라 메모리 매핑에 실패해도 OOM으로 멈추지 않고 재시도를 반복하며 진행하지 못했다.

**원인 ② 진짜 병목**: loss는 답변 토큰(평균 45개)에만 거는데, 모델은 **시퀀스 전체(최대 3,064위치) × 어휘 128,256개의 logits를 fp32로** 만들고 있었다.

```
logits 한 벌  3,072 × 128,256 × 4B ≈ 1.6GB
log_softmax와 gradient까지 2~3벌
```

`prepare_model_for_kbit_training`이 `lm_head`를 fp32로 올리기 때문이다. **쓰지도 않을 3,000개 위치를 계산하느라 메모리를 다 쓰고 있었다.**

**해결**: 답변은 항상 시퀀스 끝에 있으므로, `logits_to_keep=K`로 끝 K위치만 `lm_head`를 통과시킨다.

python

```python
def collate(features):    batch = data_collator(features)    first = (batch["labels"] != -100).float().argmax(dim=1)    batch["logits_to_keep"] = int(batch["labels"].shape[1] - first.min()) + 1    return batch
```

loss 정의는 바꾸지 않았다. HF 기본 loss와 `tail_loss`를 같은 샘플로 계산해 상대오차 1e-3 이하임을 확인했다.

|  | 수정 전 | 수정 후 |
| --- | --- | --- |
| GPU 최대 할당 | 14.1GiB | 9.89GiB |
| 예약 | 15.1GiB | 10.67GiB |
| 메모리 경고 | 반복 | 0건 |

> `gradient_checkpointing`을 켜는 것이 첫 대응이었지만, 확인해보니 이미 켜져 있었다(셀 4와 `prepare_model_for_kbit_training` 양쪽에서). 증상만 보고 흔한 처방을 하기 전에 **실제로 무엇이 메모리를 쓰는지** 확인해야 했다.
> 

#### 8-2. 학습 데이터

| 구분 | 건수 |
| --- | --- |
| train | 4,811 (511단위) |
| val | 532 (55단위) |
| distract (정답 + 방해) | 3,164 (65.8%) |
| gold_only (정답만) | 1,163 (24.2%) |
| no_answer (답 없음) | 484 (10.1%) |

목표 비율(70/20/10)과 조금 다르다. 답 없음이 될 수 있는 QA는 모두 정답+방해도 될 수 있으므로, 답 없음 10%만큼 정답+방해 몫이 줄어든다.

**val은 `unit_id` 단위로 나눴다.** train과 겹치는 단위는 0개다. 무작위로 나누면 같은 조항의 비슷한 질문이 양쪽에 들어가 val loss가 실제보다 낮게 나온다.

**토큰 길이**: 평균 1,209 / 중앙 1,073 / p90 2,057 / 최대 3,064. 설계 때 추정한 1,500보다 짧았다.

> 이전 방식(발췌 없음)은 샘플당 약 250토큰이었다. 발췌를 넣으면서 epoch당 학습 토큰이 4.5배로 늘었다. "5,343건은 적지 않은가"라는 우려에 대한 답이기도 하다.
> 

#### 8-3. 학습 결과

```
소요 2시간 50분, GPU 최대 9.89GiB
```

| step | Training Loss | Validation Loss |
| --- | --- | --- |

| 100 | 0.4234 | 0.4072 |

step 300에서 train이 0.3584 → 0.2716으로 크게 떨어진 것은 2 epoch 끝물에 같은 데이터를 두 번째 보면서 생긴 변화다. val이 따라 오르지 않았으므로 아직 암기 단계는 아니다.

> 학습을 더 돌려도 됐을 수준이지만, 2 epoch로 고정한 설계를 유지했다. 더 돌릴지는 다음 절의 실제 답변 품질을 보고 정한다.

#### 8-4. 생성 샘플 — 유형별로 다르게 나왔다

학습 직후 세 유형을 하나씩 확인했다.

**정답 + 방해 발췌 (성공)**

```
질문: 이 보험계약의 주된 목적은 무엇인가요?   (발췌 3개, 정답 위치 1)
목표: 피보험자의 상해에 대한 위험을 보장하는 것입니다.
생성: 피보험자의 상해에 대한 위험을 보장하는 것입니다.
```

발췌 세 개 중 두 번째에 있던 정답을 정확히 골랐다. **관련 없는 발췌를 무시하는 법을 배웠다.** C안을 택한 이유가 여기서 확인된다.

**정답 발췌만 (성공)**

```
질문: '뚜렷한 시야 장해'란 무엇을 의미하며, 어떻게 평가하나요?
생성: 한 눈의 시야 범위가 정상시야 범위의 60% 이하로 제한된 경우를 말합니다.
      이 경우 공인된 시야검사방법으로 측정하며, 자동시야검사계(골드만 시야검사)를
      이용해 8방향 시야범위 합계를 정상범위와 비교하여 평가합니다.
```

수치(60%)와 검사명이 정확하고, 문장만 조금 다르게 다듬었다.

**답 없음 (실패)** ← 확인이 필요한 지점

```
질문: 이 특별약관은 어떤 상황에서 적용될 수 없나요?   (발췌 2개, 정답 없음)
목표: 제공된 약관 발췌에서는 확인되지 않는 내용입니다.
생성: 이 특별약관은 모든 피보험자 또는 모든 보험수익자가 장애인이 아닌 경우,
      그리고 현재 법정상속인이 장애인이라고 하더라도 수익자 지정이 필요한 경우에
      적용될 수 없습니다.
```

**발췌에 답이 없는데 그럴듯한 답을 만들어냈다.** `no_answer` 샘플을 10% 넣은 목적이 "검색이 빗나갔을 때 지어내지 말라"를 가르치는 것이었는데, 이 샘플에서는 작동하지 않았다.

실제 서비스에서 검색이 실패하면 상담원에게 틀린 답을 주게 되므로, **가장 위험한 실패 유형**이다.

다만 샘플 하나로 단정할 수 없다. 9절의 97문항 평가에 답 없음 20건을 포함시켜 거절률을 측정한다. 거절률이 낮으면 다음 중 하나를 검토한다.

| 방안 | 내용 |
| --- | --- |
| no_answer 비율 상향 | 10% → 20% |
| 방해 발췌 기준 강화 | 지금도 답 없음 샘플은 엄격하게 고르지만(참조까지 8자 겹침 검사 + 핵심 명사 50% 관문) 더 올릴 수 있다 |
| 거절 문장 다양화 | 지금은 고정 문장 하나만 학습한다 |

#### 평가 설계

| 구분 | 모델 | 문항 | 거절 | 근거 반영 | 평균 길이 |

거절 문구는 36건 모두 토씨 하나 다르지 않았다. 판단의 결과가 아니라 **하나의 출력 모드를 외운 것**이다.

#### 답한 것은 베이스보다 낫다

> R007 "보장은 정확히 언제부터 시작되는 거예요?"
> 
> 
> **FT**: 회사가 청약을 승낙하고 제1회 보험료를 받은 때부터 보장을 시작합니다. 자동이체나 신용카드는 해당 정보가 제공된 때를 기준으로 합니다.
> 
> **베이스**: (같은 내용에 "따라서 보험료가 정상적으로 납입된 시점부터 보장이 개시됩니다" 등 중복 문장 추가, 2배 길이)
> 

파인튜닝의 목적(상담 창구에서 쓸 수 있는 간결한 말투)은 달성됐다. **답해야 할 때 거절하는 것만이 문제다.**

#### 원인 추적 — 어휘 겹침

학습 데이터를 측정한 결과:

|  | 질문-발췌 바이그램 겹침 |
| --- | --- |
| 양성 샘플 | 0.58~0.59 |
| no_answer 샘플 | 0.34 |

no_answer의 방해 발췌를 `pick_distractors`가 "답변 핵심 명사 50% 미만·같은 조 제외"로 고른다. 그 결과 **"질문 어휘가 발췌에 없으면 거절"**이 가장 쉬운 구분 단서가 되었고, 모델이 그것을 학습했다.

최소쌍이 이를 확증한다. 같은 조문·같은 발췌인데 등급을 언급하면 거절로 바뀐다.

```
제35조  R001 "해지하면 환급금 언제 들어와요?"        → 답함
        R056 "고급형인데 해지하면 환급금 있나요?"     → 거절
```

"고급형"이 발췌에 없다는 이유로 거절한다. 바로 옆에 "3영업일"이 적혀 있는데도.

거절 분포에서도 등급언급_타섹션이 15/19(78.9%)로 가장 높다. 반대로 한도·별표·꼬리는 0%다 — 계산·표 기반 질문은 멀쩡하다.

#### 실험 B — 발췌에 공통 적용 표기 추가 (폐기)

coverage_type이 None인 단위의 발췌 끝에 "이 조항은 가입 등급·유형과 관계없이 공통 적용됩니다" 한 줄을 추가했다. 의료비 특약은 유형이 특약명에 고정돼 있어 다른 문구를 썼다.

| 그룹 | 해소 |
| --- | --- |
| 등급 거절 15건 | **1건 (6.7%)** |
| 등급 외 거절 21건 | **7건 (33%)** |

**대조군이 더 많이 풀렸다.** 등급 정보를 채운 효과가 아니라 프롬프트가 한 줄 길어진 효과다.

베이스 모델도 전 구간에서 거절 수가 변했고(0→3, 2→5, 7→6), 답변 동일은 8/117에 그쳤다. 한 줄 추가로 생성 전체가 흔들렸다는 뜻이다.

no_answer 거절은 14→15로 유지됐고 근거 반영도 53→62로 올랐지만, **왜 좋아졌는지 설명할 수 없는 설정**이라 채택하지 않았다.

> 대조군을 미리 정해둔 것이 결론을 뒤집었다. 등급 거절만 봤다면 "1건 해소, 효과 미미" 정도로 넘어갔을 것이다. 등급 외 21건이 더 많이 풀린 것을 보고서야 가설 자체가 틀렸음을 알았다.
> 

#### 실험 A — 질문에서 등급 어구 제거

반대 방향. 발췌가 아니라 질문을 고친다.

```
"고급형인데 해지하면 환급금 있나요?"  →  "해지하면 환급금 있나요?"
```

등급은 이미 SearchScope가 검색 필터로 소비했다. "종·등급·유형은 UI/필터가 확정하고 모델은 추론하지 않는다"는 설계 원칙을 추론 단계까지 적용하는 것이다.

coverage_type이 지정된 단위(R026~029, R080 "고급형 수술 한도가 얼마인가요?")는 등급이 답을 가르므로 건드리지 않았다.

→ 전량 재생성 전에 소규모 검증을 먼저 한다(실험 C).

#### 미반영 사항

`train.jsonl`은 사람 대상 조항 제외 규칙 이전에 만들어졌다. 제외 대상 863건(18%)이 그대로 들어 있다 — 보통약관 제24조 14건, 장해분류표 561건 등. 코드(`faq_units.EXCLUDE_ARTICLES`)에는 반영됐으나 데이터는 재빌드되지 않았다.

#### 다음 — distractor 선정 방식

평가와 별개로 확인된 설계 결함.

현재 no_answer의 방해 발췌는 **질문과 동떨어진 조문**이다. 그래서 어휘를 세는 것만으로 구분할 수 있다.

실제 검색이 가져오는 오답은 성격이 다르다. "해지"로 검색하면 해약환급금·임의해지·연체해지가 모두 나온다 — **어휘는 겹치지만 답이 아닌 것들**이다.

방해 발췌를 검색 결과에서 뽑으면 어휘 겹침으로는 구분할 수 없게 되고, 조문을 읽어야만 판단할 수 있다.

이것은 `finetune_data.pick_distractors` 수정이며 **FAQ 재생성과 독립적**이다. 재생성 없이 재학습만으로 시험할 수 있다.

#### 10-2. 재평가 — 숫자는 그대로, 분별은 올랐다

| 구분 | 모델 | 문항 | 거절 | 근거 반영 | 평균 길이 |
| --- | --- | --- | --- | --- | --- |

문항 단위로 비교하면 숫자보다 많이 움직였다. 베이스 답변 117건이 모두 어제와 같았으므로 입력은 동일하다.

- **새로 푼 문항 4건** — R021, R025, R045, R049. 넷 다 evidence 문구가 들어 있다
- **새로 막힌 문항 3건** — R066은 어제도 근거가 없었다. R064는 어제 답("만 8세")이 발췌에 실제로 있었으므로 회귀다 — 발췌에 "생후 60일 이하 또는 만 8세(실속형 만 10세)를 초과하는 개"가 있다. **실제 후퇴는 R064·R099 2건**이다
- **둘 다 거절한 32건**이 움직이지 않은 덩어리다

**35건 중 5건은 평가 스크립트 문제였다.** `answer_eval` 이 evidence 문구가 조 제목에 걸려 제목만 있는 청크를 골랐다(R004·R009·R062·R063·R090). 발췌에 본문이 없었으므로 거절이 맞는 동작이다.

따로 전수 점검해 라벨을 나눔 — answerable 85건, partial 10건, flawed 2건이다. partial 은 "거절도 변호 가능"한 것들이고(환급금 4건은 지급 기한만 있음 등), flawed 는 질문 자체가 답을 하나로 정하지 못하는 것이다(R026·R029).

**그래서 엄밀한 거절 오류는 35건이 아니라 21건이다.**

`no_answer` 분별이 2 → 15로 오른 것은 라벨 정리의 효과다. 그러나 gold 거절은 그것으로 풀리지 않았다.

#### 10-3. 거절을 가르는 것은 길이가 아니다

파인튜닝 모델의 gold 평균 답변이 70자로 거절문(62자)과 비슷해 "짧게 답하기를 과하게 배웠다"고 보았으나, 측정 결과 **길이가 아니라 질문-발췌 겹침이었다.**

| 평가 그룹 | 건수 | p25 | 중앙 | p75 |
| --- | --- | --- | --- | --- |
| 둘 다 거절 | 32 | 0.133 | 0.188 | 0.222 |
| 둘 다 답함 | 58 | 0.188 | 0.294 | 0.364 |
| no_answer(평가) | 20 | 0.242 | 0.353 | 0.444 |
- 겹침 0.30 이상이면 거의 답한다 — 28건 중 2건만 거절
- 0.30 미만은 반반이다 — 69건 중 33건(48%) 거절. 겹침 0.00인데 답한 문항도 있다
- 가장 잘 가르는 임계값 0.23에서 정확도 70%. 전부 답한다고 쳐도 64%이므로 겹침이 더하는 것은 6%p다. AUC 0.71

**겹침만으로는 갈리지 않는다.** 남은 차이는 등급 어구로 설명된다 — 겹침 0.3 미만에서 거절된 33건 중 17건이 등급 어구 문항이고, 답한 36건에는 3건뿐이다. 9절의 최소쌍(R001 답함 / R056 거절)이 보여준 것이 전체에서도 확인된다.

| 0.1~0.2 | 76% | 44% |

| 0.3~0.4 | 35% | 19% |
| 0.4 이상 | 4% 이하 | 5% 이하 |

학습 전체의 no_answer 비율은 10%인데 0.1~0.3 구간에서는 27~44%로 올라간다. 평가 거절률도 이 비율을 따라 움직인다. **"겹침이 낮으면 모른다고 한다"를 배운 것으로 본다** — 같이 움직이는 것을 본 것이지 인과를 직접 잰 것은 아니다.

질문 길이도 같은 방향이다. 평가 질문은 중앙 26자인데 학습셋에서 30자 이하는 2.4%(163건)뿐이고 그중 no_answer가 17.8%다. 60자 넘는 질문에서는 8.2%다.

**평가 세트가 학습 분포의 끝에 몰려 있다.** 둘 다 거절한 문항의 겹침 중앙 0.188은 학습 양성 기준 하위 10.7%, 둘 다 답한 문항의 0.294도 하위 9.3%다.

#### 10-5. 재작성은 원인이 아니다

"구어체로 바꾸면서 질문이 발췌에서 멀어져 거절이 늘었다"는 가설을 같은 학습 표본에서 질문만 원래대로 되돌려 검증했다(매칭 실패 0건).

|  | 재작성 후 | 원래 질문 |
| --- | --- | --- |
| 양성 겹침 중앙 | 0.464 | 0.585 |
| no_answer 겹침 중앙 | 0.298 | 0.368 |
| 0.1~0.2 구간 NA 비율 | 44% | 77% |
| 0.2~0.3 구간 NA 비율 | 27% | 50% |

겹침은 함께 내려갔지만 **낮은 구간의 no_answer 비율은 오히려 줄었다.** 재작성은 지름길을 약하게 만들었다. 되돌리지 않는다.

그런데도 거절이 남은 것은 두 가지 때문이다. 약해진 뒤에도 그 구간이 학습 전체 평균의 3~4배이고, 평가 질문의 44%가 겹침 0.2 미만 구간에 놓여 있는데 학습 양성은 108건뿐이다.

#### 10-6. 구조적 원인

no_answer 샘플은 gold 발췌를 빼고 다른 발췌를 넣어 만든다. 그러면 질문과 발췌의 겹침이 **필연적으로** 낮아진다 — 양성은 질문이 발췌를 보고 만들어지는데 no_answer는 그 발췌가 없기 때문이다.

지금 방식을 유지하는 한 이 차이는 계속 생기고, 모델은 발췌를 읽지 않고 질문 형태만 보고 라벨을 맞힐 수 있다. 9절 끝의 "distractor를 검색 결과에서 뽑는다"도 같은 문제를 다른 각도에서 본 것이다.

**더 직접적인 방법은 같은 질문을 양쪽에 넣는 것이다.** no_answer에 쓴 QA의 질문을 gold 발췌와 함께 양성으로도 넣으면, 질문만 보고는 라벨을 맞힐 수 없고 발췌를 읽어야만 갈린다. 지금은 양쪽에 다 나오는 질문이 11개뿐이다.

#### 10-7. 다음 재구축에서 바꿀 것

우선순위 순이다.

1. **같은 질문으로 양성과 no_answer 쌍을 만든다.** 지름길을 직접 끊는 방법이라 가장 효과가 클 것으로 본다
2. **방해 발췌을 검색이 실제로 가져올 오답으로 바꿜다.** 지금 1,351개 중 970개(72%)가 다른 문서이고 인접 조는 184개(14%)뿐이다. 같은 조의 다른 항, 같은 특약의 인접 조로 바꾼다. FinRAG-12B 도 거절 보정 데이터를 "주제상 관련 있으나 정답을 담기엔 부족한 발췌"로 만든다. 9절 끝에 적어둔 것과 같은 변경이고, 1번과 같은 build 단계다
3. **짧은 구어체 양성 질문을 늘린다.** 재작성에 "20~35자" 변형을 하나 더 두고, 겹침 0.3 미만 양성을 수백 건 단위로 늘린다. 지금 30자 이하는 2.4%, 겹침 0.2 미만 양성은 108건이다
4. **등급 어구가 붙은 공통 조항 양성을 늘린다.** 138건을 바꿔 보는 것(9절 실험 B)으로는 풀리지 않았다. 학습 데이터에서 다뤄야 한다
5. **빌드 단계에 검사를 넣는다.** 겹침 구간별 no_answer 비율을 `stats.json`에 남기고, 0.3 미만 구간이 전체 비율의 1.5배를 넘으면 빌드를 실패시킨다. 낮은 겹침의 no_answer를 버리는 것은 분별(14~15건)을 깎을 수 있어 마지막 수단이다
