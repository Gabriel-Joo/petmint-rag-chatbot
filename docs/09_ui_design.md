#### 1. 설계 원칙

#### 1-1. 모델이 추론할 필요를 UI에서 없앤다

01~06번 전체를 관통한 원칙을 UI까지 끌고 온다.

```
강아지/고양이 구분   → 모델이 추론하지 않고 고객 정보에서 확정
등급(고급/기본/실속)  → 모델이 추론하지 않고 가입 정보에서 확정
유형(Ⅰ/Ⅱ/Ⅲ)       → 모델이 추론하지 않고 가입 정보에서 확정
```

이 셋은 모두 Milvus 메타데이터 필터로 직결된다. UI에서 확정하면 검색 후보에 다른 등급·유형이 애초에 들어오지 못한다.

> **2026-10-14 평가가 이 원칙을 역으로 확증했다.** 질문에 등급 어구가 들어가면 파인튜닝 모델의 거절률이 크게 오른다(등급 언급 문항 15/19 거절). 추론 단계에서 보정하려는 두 실험이 모두 실패했다 — 발췌에 공통 적용 표기를 추가(15건 중 1건 해소, 대조군이 오히려 7건 해소)해도, 질문에서 등급 어구를 제거(15건 중 3건 해소, 새 거절 2건)해도 풀리지 않았다. **등급이 프롬프트에 들어간 뒤에는 되돌릴 방법이 없다.** UI에서 애초에 들어가지 않게 하는 것이 유일하게 작동하는 설계다.
> 

#### 1-2. 상담 업무 흐름을 그대로 반영한다

실무에서는 고객이 전화하면 번호로 조회돼 가입 정보가 먼저 뜬다. "사용자가 종을 고른다"가 아니라 "고객 데이터가 조건을 정한다"가 실제 순서다.

그래서 고객 정보가 1-1의 필터를 자동으로 채워준다.

> **진입점은 둘이다 (10번 1·3절).** 상담원은 다른 일을 하다가 전화를 받는다 — 전화 알림은 어느 화면에서든 나타나고, 받으면 업무특화 모드로 곧바로 들어간다. 고객 조회 화면은 전화 없이 상담을 시작하는 두 번째 입구로 남는다. 둘 다 고객 하나를 정해 세션을 여는 같은 곳으로 수렴한다.
> 

#### 1-3. 상담 한 건 = 세션 하나

1:1 상담이므로 대화 중에 고객이 바뀌지 않는다. 상담이 끝나면 세션을 닫는다.

세션 단위로 로그가 묶이면 "이 상담에서 무엇을 물었고 어떻게 답했나"가 한 덩어리로 남아 품질 분석에 쓸 수 있다.

> **이 원칙은 업무특화 모드에만 해당한다 (10번 2절).** 일반·사내규정은 상담원 개인의 작업 공간이라 "새 대화" 버튼으로 끊기 전까지 세션이 유지되고, 모드를 오가도 대화가 보존된다. 로그가 세션 단위로 묶이는 것은 세 모드 모두 같다.
> 

상담 종료 후 화면 전환과 전화 알림은 10번 문서에서 정한다.

#### 2-1. 모드 선택 — 캐릭터

세 모드의 차이를 설명문 대신 캐릭터 소개로 전달한다.

| 모드 | 소개 | 구성 |
| --- | --- | --- |
| 일반 | "약관은 모르지만 뭐든 물어보세요. 외부로 나가지 않아요" | Tri-7B 원본 |
| 사내규정 | "인사·복무 규정은 제가 알아요" | Tri-7B 원본 + 인사규정 RAG |
| 업무특화 | "펫보험 약관은 제 전문이에요. 근거 조항까지 찾아드려요" | Tri-7B 파인튜닝 + 약관 RAG |

캐릭터는 이 화면에만 크게 나온다. 상담 중에는 작은 아이콘으로 현재 모드만 표시한다 — 고객 전화를 받으며 쓰는 도구라 산만하면 안 된다.

#### 2-2. 고객 조회

고객마다 카드 하나다. 탭 둘로 나눈다.

| 탭 | 내용 |
| --- | --- |
| 전체 | 고객 목록 전부 |
| 최근 상담 | 상담한 순서대로. 기록이 없으면 비어 있다 |

**최근 상담 탭이 필요한 이유**: 전화가 무작위로 오므로 방금 통화한 고객이 목록 어딘가에 묻힌다. "아까 그 고객"을 다시 찾을 때 바로 보여야 한다. 세션 기록이 채워주므로 MySQL 연동 후에 제대로 동작한다(6-3절).

> **종 조합으로 나누던 카드 3종(둘 다 보유 / 강아지만 / 고양이만)은 폐기했다 (2026-10-14).** 세 분류의 유일한 차이는 "종 토글을 띄우느냐"였는데, 토글이 종이 아니라 **반려동물 개체 선택**으로 바뀐다(2-3절). 개체를 고르면 종이 따라오고 거기서 약관이 정해지므로, 고객을 종 조합으로 나눌 이유가 없다. 강아지 2마리를 기르는 고객이 어느 분류에도 제대로 들어가지 않았던 것도 같은 이유다.
> 
> 
> 다만 **샘플 고객 10명은 여러 경우를 덮어야 한다** — 한 종만, 두 종 보유, 같은 종 여러 마리, 통원·입원 등급이 다른 경우, 부담보가 있는 경우. 이것은 픽스처 구성의 문제지 UI 분류의 문제가 아니다.
> 

| 카드 | 상황 | 상담 화면에서 |
| --- | --- | --- |
| 고객 조회 | 전체 탭과 최근 상담 탭 | 고객과 반려동물이 정해진다 |

**과거 상담 목록 — 같은 것을 두 곳에서 부른다**

고객 하나에 딸린 목록 하나다(`sessions`에서 그 `customer_id`를 `started_at` 역순). 컴포넌트도 하나고, 부르는 자리만 둘이다.

| 자리 | 상황 | 여는 방식 |
| --- | --- | --- |
| 고객 조회 화면의 고객 카드 안 | 전화 없이 시작할 때 | 화면 전환해도 된다 |
| 상담 화면 상단 고객 카드 안 | 통화 중 "아까 그거" 대응 | 모달로 덮는다 |

상담 화면에서 화면을 전환하면 **진행 중인 상담을 잃는다.** 닫으면 원래 자리로 돌아와야 한다.

**전화 알림은 그대로 새 상담으로 간다.** 과거 상담은 진입점이 아니라 참고다 — 1-2절의 "고객 데이터가 조건을 정한다"가 그대로 유지된다.

**열린 과거 상담은 읽기 전용이다.** 대화·근거 패널·계산 카드가 **당시 값으로** 보인다(12번 2-2절 스냅샷). 등급이 바뀐 고객의 작년 상담을 열었는데 지금 등급으로 보이면 "그때 이렇게 안내했다"가 거짓이 된다.

**거기서 이어서 질문할 수 없다.** 두 가지 이유다 — 1-3절의 "상담 한 건 = 세션 하나"가 깨지고, 지금 통화에 물어야 할 것을 과거 세션에 붙이면 **이번 통화 로그에 남지 않아** 책임 추적이 갈라진다. 물을 것이 생기면 모달을 닫고 지금 세션에 묻는다.

> **가입 상담(비가입자) 흐름은 범위에서 뺐다 (2026-10-14).** 세 가지 이유다. 첫째, 가입 심사 기준은 인수지침·상품설명서에 있고 약관에 없다 — 근거가 없는 질문을 받으면 모델은 거절하거나 지어낸다. 둘째, 나머지 흐름은 전부 "고객 조회 → 가입 정보로 검색 필터 → 답변"인데 가입 상담만 고객이 없어 필터 기준이 없다 — 7-2절에 비가입자의 나이·종을 넘기는 방법이 정해져 있지 않았던 것도 같은 자리가 비어 있었기 때문이다. 셋째, "약관에 근거가 없는 질문은 받지 않는다"는 것 자체가 설계 판단이다.
> 
> 
> 단, 인수지침을 별도 코퍼스로 추가하면 사내규정 모드와 같은 구조로 확장할 수 있다. `SearchScope.unrestricted`는 인사규정 코퍼스가 계속 쓰므로 지우지 않는다.
> 

#### 2-3. 상담 화면

**근거 조항 패널**

| 환경 | 배치 |
| --- | --- |
| PC | 본문 오른쪽 2단 패널 |
| 모바일 | 답변 아래 접힌 영역, 탭하면 펼침 |

같은 데이터를 배치만 다르게 한다. 조항을 클릭하면 원문 전문을 보여준다.

**과거 상담**은 상단 고객 카드 안에서 모달로 열린다(2-2절). 통화 중에 화면을 전환하면 진행 중인 상담을 잃기 때문이다.

**반려동물 선택**은 고객에게 반려동물이 둘 이상일 때 상단 고객 카드에 나타난다. 종이 아니라 **개체 이름**으로 고른다 — 강아지를 두 마리 기르는 고객은 종으로는 갈라지지 않는다. 개체를 고르면 그 개체의 종·특약·등급이 검색 범위를 정한다. 상담 중에도 다른 개체로 옮길 수 있다 — "초코는 그렇고 보리는요?" 같은 질문이 나온다.

**계산 카드**: 치료비가 들어간 질문에는 `limit_table.calculate_payout` 결과를 답변 옆 카드로 보여준다. 모델은 계산에 손대지 않는다(07번 5절 참고).

**부담보 배너**: 가입한 특약에 부담보(예: 슬개골 탈구 제외)가 있고 질문이 거기 해당하면, 코드가 대조해 경고를 띄운다. 모델에게 맡기지 않는 이유는 7B가 예외·단서 추론에서 가장 많이 틀리기 때문이다.

#### 3. 검색 필터 — 설계 검토에서 발견한 결함

**상태: 구현 완료.** 회귀 세트 93문항으로 56/87 → 75/87, MRR 0.569 → 0.677 확인. 아래는 발견 경위와 설계 근거 기록.

#### 3-1. 지금 구조에 UI 필터를 그대로 넣으면 검색이 망가진다

`search_engine.py`는 등급·유형 필터를 컬렉션 전체에 건다.

python

```python
coverage_type == "고급형" and type == "Ⅱ"
```

그런데 **의료비 특약 밖의 청크는 전부 `coverage_type`이 null이다.**

```
보통약관 164건
일반조항 85 + 54건
별표·안내·법규
→ 강아지 928건 중 약 750건
```

Milvus에서 `coverage_type == "고급형"`은 null 행을 통과시키지 않는다. BM25 쪽도 마찬가지다. 의료비 특약 안에서도 등급 없는 행이 섹션마다 8~13건 있다(제2조 이후 조문).

**결과**: 고급형Ⅱ 가입자가 "계약 해지하면 환급금 있나요?"를 물으면 보통약관이 한 건도 안 나오고 의료비 특약 제1조만 돌아온다.

**지금 안 드러난 이유**: 질문에 "고급형"을 직접 쓸 때만 필터가 켜진다. UI가 가입 정보로 항상 필터를 채우면 바로 터진다. 02번의 "고급형 6유형 검출 12/12"는 한도 질문만 측정한 결과라 이 결함이 잡히지 않았다.

#### 3-2. 올바른 필터 의미

```
"가입하지 않은 특약·등급만 빼고 나머지는 전부 남긴다"

(의료비 특약이 아닌 청크는 전부 통과)
or (가입한 의료비 특약 and (내 등급 or 등급 없음))
```

`type`은 `section_name`이 이미 정하므로 따로 필터할 필요가 없다. 가입하지 않은 의료비 특약(예: 통원Ⅲ)은 통째로 빠진다.

> "여섯 유형이 모두 검색된다"(02번 6-6절)는 전제는 **필터가 없는 코퍼스(인사규정)에서만** 성립한다. 약관 모드의 고객은 자기가 가입한 유형만 본다.
> 

#### 3-3. SearchScope — 필터를 값 객체로

필터를 문자열 정규식이 아니라 값 객체로 넘긴다. Milvus 식과 BM25 술어를 한 객체에서 만들어야 둘이 엇갈리지 않는다.

```
data/search_scope.py (신규)

Subscription   section_name, coverage_type
SearchScope    species, subscriptions, focus_sections
               milvus_expr()  → Milvus 필터식
               allows(chunk)  → BM25 후보 필터, 같은 의미
               from_query()   → 기존 정규식 동작 (04번 측정 재현용)
```

`data/`에 두는 이유는 08번 Ragas 평가도 서비스와 같은 필터를 써야 하기 때문이다.

기존 `_extract_*_filter`는 지우지 않고 `from_query`로 옮긴다. 04번 측정을 같은 결과로 재현할 수 있어야 한다. 앱에서는 정규식을 **가정 질문 감지기**로만 쓴다.

**함께 바꿀 곳**: `rag_context.search_with_graph`, `build_full_context`, 04번 노트북 셀 2.

**검증**: 모든 청크에서 `scope.allows()` 개수와 Milvus `query(filter=scope.milvus_expr())` 개수가 같은지 확인한다.

#### 3-4. 참조 조문에도 등급 힌트를 준다

등급 없는 청크(예: 의료비 제4조)가 제1조를 참조하면, 지금은 3등급을 `{고급형: X / 기본형: Y / 실속형: Z}`로 병기한다. 가입자라면 자기 등급 한 벌만 붙인다.

컨텍스트가 짧아지고, 다른 등급 숫자를 섞어 말할 여지도 없어진다.

---

#### 4. 되묻기 — 조건을 다시 정의한다

필터가 걸리면 등급·유형은 섞일 수 없다. 남는 애매함은 **통원과 입원 사이**에서 생긴다.

그런데 `limit_table`을 보면 Ⅰ·Ⅱ·Ⅲ 한도는 통원과 입원이 같다. 그래서 조건은 이렇게 된다.

```
발동    상위 결과의 section_name들이 서로 다른 (유형, 등급) 조합에 대응할 때
안 함   같은 등급이면 통원/입원을 물을 필요가 없다
안 함   가입 상담 — 범위에서 제외됨. 고객 조회에서 이 카드가 안 뜬다
안 함   가정 질문 — 질문에 쓴 쪽으로 검색하고 "가입 계약 기준 아님" 배너를 띄운다
```

되묻기가 발동했는지는 `turns.clarified`에 남는다(12번 1-1절).

#### 5. 멀티턴 — 백엔드에서 처리한다

"그럼 입원은요?" 같은 후속 질문은 그대로는 검색이 안 된다.

**대화 이력을 프롬프트에 넣지 않는다.** 학습 데이터가 전부 2턴(`system`, `user`)이라 형식이 달라지면 재학습이 필요하다(07번 6절).

| 방법 | 내용 |
| --- | --- |
| 질문 재작성 | 이력 + 후속 질문 → 독립 질문. 모델에는 완성된 질문 하나만 간다 |
| 앞 턴 발췌 이월 | 직전 턴의 상위 발췌를 이번 발췌 목록에 추가. 형식이 그대로라 학습 형식을 안 깬다 |

**재작성기는 베이스 모델을 쓴다.** 파인튜닝 모델은 "발췌를 읽고 상담 말투로 답하기"만 배우므로, 재작성을 시키면 질문을 다시 쓰지 않고 답을 해버릴 가능성이 크다.

**재작성된 질문을 화면에 보여준다.** 상담원이 "내 질문이 저렇게 해석됐구나"를 알 수 있고, 틀렸으면 바로 고쳐 물을 수 있다.

```
┌──────────────────────────────┐
│ 그럼 입원은요?                 │  ← 상담원이 쓴 것
│   ↳ 고급형 입원 수술 한도는?    │  ← 재작성 (작게)
├──────────────────────────────┤
│ 입원 중 수술한 날의 한도는...    │
└──────────────────────────────┘
```

**"더 짧게", "고객에게 말하듯이 다시"** 같은 고쳐쓰기는 검색 질의 문제가 아니라 직전 답변을 입력으로 받는 다른 작업이다. UI 버튼으로 받아 베이스 모델에 넘긴다. 약관 사실은 이미 직전 답변 안에 있으므로 베이스 모델로도 된다.

**비용**: Ollama가 같은 GPU에서 두 모델을 갈아 끼우는 지연이 생긴다. VRAM 예산을 볼 때 함께 본다.

#### 6. 데이터 스키마

#### 6-1. 고객 — 특약 단위로 간다

약관을 확인한 결과, 등급은 특약마다 따로 정의된다. 6개 의료비 특약이 각각 제1조에 고급형·기본형·실속형 블록을 둔다. 한도는 "보험증권에 기재된" 값으로 적혀 있어 특약별로 증권에 들어간다.

다만 **"통원과 입원을 같은 등급으로 가입해야 한다"는 조항도, "다르게 가입할 수 있다"는 조항도 약관에 없다.** 이런 조합 규칙은 상품설명서나 사업방법서에 있고 우리 PDF에는 없다.

가능 여부와 무관하게 특약 단위 스키마로 확정한다. 구조가 더 일반적이기 때문이다.

json

```json
{
  "customer_id": "C001",
  "name": "김보호",
  "phone": "010-1234-5678",
  "pets": [
    {
      "pet_id": "P001",
      "name": "초코",
      "species": "강아지",
      "breed": "포메라니안",
      "age": 3,
      "policies": [
        {
          "doc_id": "petmint_dog_2604",
          "product_name": "무배당 펫퍼민트 Puppy&Family보험 다이렉트2604",

          "section_name": "펫퍼민트 반려견 통원의료비Ⅱ보장 특별약관",

```

| 필드 | 쓰임 |
| --- | --- |
| doc_id | 어느 약관 문서에 가입했는지. 지금은 화면 표시용이고, 문서가 늘면 검색 필터로 승격한다 |
| product_name | 표시용. doc_id로 끌어올 수 있지만, 고객 레코드만 봐도 사람이 읽을 수 있게 둔다 |
| policy_version | 같은 상품의 개정판을 구별하는 유일한 값. doc_id에는 버전이 들어 있지 않다 |
| section_name | 검색 필터. 청크의 section_name과 같은 문자열이어야 한다 |
| coverage_type | 검색 필터 + 계산 카드 |
| copay | 자기부담금 3만/5만. 계산 카드 |
| contract_date | 보장개시·면책기간 판단 (의료비 제1조 30일·1년 단서) |
| excluded_conditions | 부담보. 코드가 질문과 대조해 배너 |

**약관 문서의 속성은 복사하지 않는다.** `effective_date`·`expiry_date`는 고객이 아니라 약관의 것이라 고객 레코드에 복사하면 개정 시 두 군데가 어긋난다. 화면에 띄울 때 `doc_id`로 청크 메타에서 조회한다.

**가입일은 판매개시일 이후여야 한다.** 초기 픽스처는 `contract_date`가 2025-03-01인데 약관 `effective_date`는 2026-07-13이었다 — 존재하지 않던 약관에 가입한 셈이다. 로더가 이것도 검증한다.

`type`은 담지 않고 `section_name`에서 계산한다. 값을 두 곳에 두면 어긋날 수 있다.

**로더가 검증한다.** `section_name`이 실제 청크에 있는 값인지 확인하고, 하나라도 어긋나면 기동을 실패시킨다. 오타가 나면 필터가 조용히 0건이 되기 때문이다.

**샘플 고객 10명 중 1~2명은 통원·입원 등급을 다르게 넣는다.** 실제로 불가능한 조합이라도 구조가 처리할 수 있는지 시험하는 용도다.

#### 6-2. 세션

json

```json
{
  "session_id": "uuid",
  "mode": "업무특화",
  "customer_id": "C001",
  "started_at": "...",
```

`pet_id`는 메시지에만 담고 세션에는 두지 않는다. 두 곳에 두면 개체 선택과 질문 사이에 값이 엇갈릴 수 있다. 서버는 메시지의 `pet_id`가 세션 고객의 것인지 검증하고 기록한다.

**세션 수명**: 초안은 메모리였고, 그래서 재시작하면 사라졌다. **로그를 MySQL로 옮기기로 했으므로 세션도 같은 DB에 둔다**(6-3절) — 재시작해도 남는다. WS 재연결 시 4404를 받으면, 업무특화는 고객 조회로 돌아가고 일반·사내규정은 그 모드의 빈 대화창에서 새 세션을 연다 — 고객 조회가 없는 모드라 돌아갈 곳이 없다.

> **30분 무활동 정리는 없앴다 (2026-10-15).** 메모리 저장소 시절의 유물이다. 세션이 DB에 남으므로 일반·사내규정은 닫히지 않고 이어 쓸 수 있다. 업무특화는 상담 종료로 닫힌다.
> 
> 
> **모드마다 수명이 다르다 (10번 2절).** 세 모드의 세션이 동시에 존재할 수 있다.
> 

**보존**: 세션 메모리(대화 문맥)는 종료 시 지운다. 로그는 남긴다. 둘을 분리하면 "지운다/남긴다"가 충돌하지 않는다.

#### 6-3. 로그

json

```json
{
  "turn_id": "uuid",
  "session_id": "uuid",
  "customer_id": "C001",
  "pet_id": "P001",
  "agent": "...",
  "mode": "업무특화",
  "scope": { },
  "hypothetical": false,
  "clarified": false,
  "question": "...",
  "rewritten_question": "...",
  "answer": "...",
  "retrieved": [{"graph_key": "...", "score": 0.72, "content": "..."}],
  "used_references": [ ],
  "model": "...",
  "prompt_version": "rag-1",
  "index_version": "...",
  "first_token_ms": 480,
  "latency_ms": 2300,
  "status": "ok",
  "timestamp": "..."
}
```

**`turn_id`가 필요한 이유**: 피드백 버튼이 가리킬 대상이 있어야 한다. 모든 서버 메시지와 로그에 넣는다.

**`retrieved`에 본문까지 남기는 이유**: 08번 Ragas는 질문·답변·컨텍스트가 모두 필요하다. 키는 `rag_context.graph_key`를 쓴다 — Milvus auto_id는 재색인하면 바뀌므로 쓰지 않는다.

**`prompt_version`·`index_version`**: 이 값이 없으면 로그를 나중에 비교할 수 없다.

**전화번호와 이름은 로그에 넣지 않는다.** `customer_id`만 남긴다.

**저장소는 MySQL이다 (2026-10-14 변경).** 초안은 JSONL 파일이었다 — 쓰기만 하고 08번 평가에서 통째로 읽으면 충분했기 때문이다. 그러나 상담 내역(고객별·기간별 조회)을 붙이면 매번 파일을 처음부터 훑어야 한다. 세션도 DB로 가면 재시작 시 소멸 문제가 풀린다(6-2절).

테이블은 **다섯**이다. 칼럼 상세는 12번 1-1절이 기준이다.

| 테이블 | 내용 |
| --- | --- |
| sessions | session_id, mode, customer_id, agent_email, title, 시작·종료 시각, deleted_at, pinned |
| turns | turn_id, session_id, 질문, 재작성된 질문, 답변, 반려동물 스냅샷, is_hypothetical, clarified, 모델, prompt_version, index_version, first_token_ms, latency_ms, status, payout |
| turn_scope | 그 턴에 적용된 가입 내용. 특약 하나당 한 줄 |
| retrieved | turn_id별 검색 결과. 본문까지 남기므로 행이 가장 많다. 그래프로 따라간 조문도 via_graph로 표시해 함께 남긴다 — 그쪽은 청크가 아니라 graph_key·rank·score가 없다 |
| feedback | turn_id, 평가. 원본 로그는 고치지 않는다 |

**인덱스는 화면이 정한다.** 상세는 12번 1-1절에 있다. 지난 대화 목록은 `(agent_email, mode, deleted_at, started_at)`, 최근 상담 탭은 `started_at`, 고객별 내역은 `customer_id`다.

**MySQL 인스턴스는 클러스터에 하나만 둔다.** StatefulSet + PVC. 데이터베이스를 `petmint`와 `runshoes`로 나누고, 계정도 둘로 나눠 각자 자기 데이터베이스만 접근하게 한다. Secret은 네임스페이스별로 둔다.

> 인스턴스를 나누지 않는 이유: 데이터베이스가 다르면 데이터는 섞이지 않지만, 같은 프로세스라 한쪽이 죽으면 둘 다 죽는다. 그런데 둘 다 포트폴리오고 트래픽도 없으므로, 16GB에 GPU 모델들이 올라가는 것을 생각하면 인스턴스 둘은 아깝다. 계정 분리로 최소 권한은 지킨다.
> 

**피드백**은 `feedback` 테이블에 `turn_id`를 키로 따로 쓴다. 원본 로그는 고치지 않는다.

#### 7. API 설계

#### 7-1. REST

```
GET    /api/customers              고객 목록
GET    /api/customers/{id}         고객 상세
GET    /api/customers/{id}/sessions  그 고객의 과거 상담 목록 (2-2절)
GET    /api/sessions               지난 대화 목록 (agent_email로 거름, deleted_at IS NULL)
POST   /api/sessions               세션 시작 (mode, customer_id)
GET    /api/sessions/{id}          세션 상세 — 턴과 근거까지 한 번에
PATCH  /api/sessions/{id}          제목 변경, 고정 등
DELETE /api/sessions/{id}          상담 종료 / 목록에서 제거(deleted_at)
GET    /api/consultations/recent   최근 상담 탭 — 고객 단위, 상담원으로 거르지 않는다
GET    /api/articles/{species}/{section}/{section_name}/{article_num}
POST   /api/turns/{turn_id}/feedback
```

**읽기와 쓰기가 다르다.** 세션을 바꾸는 작업(PATCH·DELETE·WS·피드백)과 내 목록(`GET /api/sessions`)은 `agent_email`로 거르고, 남의 것은 없는 세션과 같게 404다. 반면 **읽기(`GET /api/sessions/{id}`)는 고객이 있는 세션에 한해 남의 것도 열어준다.**

최근 상담 탭 자체가 "다른 상담원이 받은 고객도 다시 전화한다"는 전제 위에 있다(2-2절). 고객은 보이는데 무슨 얘기를 했는지를 못 보면 탭이 반쪽이고, 상담원이 고객에게 "아까 뭐라고 안내받으셨어요?"를 되묻게 된다. 13번 2-1절의 "통과한 사람 = 상담원"은 외부인을 막는 것이지 상담원끼리 기록을 가리자는 것이 아니다.

일반·사내규정 세션은 이 경로로 열리지 않는다 — `customer_id`가 없어 과거 상담 목록에 뜨지 않고, 남의 개인 작업 공간이다.

응답에는 그 상담을 담당했던 `agent_email`을 넣는다. 누가 안내한 내용인지 화면에 보여야 한다.

**최근 상담만 상담원 필터가 없다.** 지난 대화 목록(일반·사내규정)만 상담원 것으로 거른다.

조항 원문 API에 Milvus id를 쓰지 않는다. 재색인하면 바뀌기 때문이다. 구조 경로로 받아 `ContextBuilder.fetch_article_content`를 그대로 쓴다.

```
  {"type": "done", "turn_id": "...", "latency_ms": 2300, "first_token_ms": 480}
```

**`sources`를 먼저 보내는 이유**: 검색 결과는 생성 전에 이미 나와 있다. 먼저 보내면 근거 패널이 0.5초 안에 찬다. 답변이 실제로 쓴 것(`used_references`)은 생성이 끝나야 알 수 있으므로 나중에 `references`로 보낸다.

**`cancel`을 처음부터 넣는다**: 생성 중에 새 질문이 오거나 상담이 끝나면 Ollama 스트림을 취소해야 한다.

**스트리밍을 쓰는 이유**: 7B가 500자를 만들면 5~10초다. 통째로 기다리면 빈 화면이고, 흘려보내면 0.5초 만에 첫 글자가 나온다. 같은 10초인데 체감이 다르다.

#### 7-3. 프로세스 모델

**GPU를 쓰는 것은 전부 호스트에, Pod는 네트워크로 호출한다.**

GPU 패스스루를 하지 않기로 했으므로 K8s Pod에서는 GPU를 쓸 수 없다. 그런데 이 서비스는 GPU를 두 곳에서 쓴다 — 검색(KURE 임베딩 + bge-reranker)과 생성(Ollama)이다. 생성은 이미 호스트 Ollama를 호출하는 구조이므로, **검색도 같은 방식으로 호스트 서비스로 빼낸다.**

```
[GPU 호스트]
  Ollama           :11434   생성
  search-service            KURE + bge-reranker + Milvus 조회
       ↑ 네트워크 호출
[K8s Pod]
  FastAPI 앱              세션·필터·계산·조립 (GPU 미사용)
```

**대안과 비교**: 검색을 CPU로 돌리는 방법은 리랭커가 후보를 쌍으로 비교하는 구조라 지연이 크게 늘어난다 — 고객 전화를 받으며 쓰는 도구에 맞지 않는다. Pod에만 GPU를 할당하는 방법은 패스스루를 하지 않기로 한 결정과 충돌한다.

**얻는 것**: 검색 모델이 앱 프로세스에서 빠지므로 **uvicorn worker를 1개로 제한할 이유가 없어진다.** 세션이 DB에 있으므로 worker를 늘려 동시 접속 여력을 키울 수 있다.

**개발 중에는 분리하지 않는다.** `data/search_engine.py`는 그대로 두고, 그것을 감싸는 얇은 HTTP 래퍼만 따로 둔다. 노트북 01~08은 지금처럼 직접 import하고, 서비스만 HTTP로 호출한다 — 평가와 서비스가 같은 코드를 쓰는 원칙(3-3절)이 깨지지 않는다.

`rag_context`는 engine 객체를 받아 `engine.search(query, scope, ...)`를 호출한다. 따라서 **같은 `search` 메서드를 가진 HTTP 클라이언트를 넘기면 `rag_context`를 고치지 않아도 된다.** 노트북은 진짜 엔진을, 서비스는 클라이언트를 넣는다.

**VRAM 예산을 계산해야 한다.** 16GB(RTX 5070 Ti) 하나에 아래가 함께 올라간다.

| 모델 | 상주 여부 |
| --- | --- |
| KURE 임베딩 | 상시 (search-service). 정밀도를 지정하지 않아 현재 fp32로 올라간다 — 빠듯하면 fp16으로 내릴 수 있다 |
| bge-reranker-v2-m3 (fp16, 1024) | 상시 (search-service) |
| Tri-7B 원본 (Q4_K_M) | 일반·사내규정 모드, 재작성기 |
| Tri-7B 파인튜닝 (Q4_K_M) | 업무특화 모드 |

**검색 모델 둘은 상시 상주이고 Ollama 모델만 갈아 끼우는 구조다.** 따라서 `OLLAMA_MAX_LOADED_MODELS`와 `keep_alive`는 16GB에서 검색 모델 몫을 먼저 뺀 나머지로 정해야 한다.

**둘이 함께 올라갈 수 있는지는 모드 전환 때만의 문제가 아니다.** 업무특화 모드는 한 턴 안에서 원본으로 질문을 재작성하고(5절) 파인튜닝으로 답한다 — **매 턴 두 모델을 다 쓴다.** 둘 다 상주가 가능하면 `OLLAMA_MAX_LOADED_MODELS=2`로 두고, 불가능하면 턴마다 갈아 끼우며 그 지연을 `first_token_ms`로 측정한다.

실측 전까지 수치를 단정하지 않는다. `nvidia-smi`(전체·프로세스별)와 `docker exec ollama ollama ps`로 재고, search-service 기동 직후와 Ollama 생성 중을 나눠 측정한다.

**재부팅 대응**: Ollama 컨테이너가 `restart=no`다. systemd 유닛에 Ollama·Milvus 의존성을 넣거나 재시작 정책을 바꿔야 한다.

K8s 배포 후에는 systemd 대신 Deployment와 probe가 이 역할을 한다. Ollama는 GPU 호스트에 그대로 두고 Pod가 네트워크로 호출하므로, 컨테이너화 대상은 FastAPI 앱과 React 빌드물뿐이다.

> **파인튜닝 모델은 GGUF 변환이 필요하다.**
> 
> 
> LoRA 어댑터 + 베이스 병합 → GGUF 변환(llama.cpp) → 양자화 → Modelfile → ollama create
> 
> **양자화를 베이스와 같은 Q4_K_M으로 맞춘다.** 다르면 모드 간 차이가 파인튜닝 효과인지 양자화 차이인지 구분되지 않는다. 변환 후 97문항 평가를 다시 돌려 양자화로 인한 성능 변화를 확인한다.
> 

#### 7-4. 인증

Cloudflare Access를 쓴다. 이 화면들은 고객 이름과 전화번호를 보여주므로 터널을 열기 전에 인증이 있어야 한다.

Access는 코드가 0줄이다. 앱은 `Cf-Access-Authenticated-User-Email` 헤더만 읽어 상담원 ID로 로그에 남긴다. 내부망 직접 접속에는 헤더가 없으므로, 내부망도 터널을 거치게 하거나 개발용 기본값을 둔다. 상세는 13번 문서다.

#### 9. 정하지 못한 것

- **"사내규정" 모드의 데이터** — 가상 인사규정 전처리 완료(청크 49개, 참조 그래프 7엣지, 회귀 세트 24문항). Milvus 색인만 남았다.
- **멀티턴 재작성의 실제 품질** — 재작성이 충분한지 측정하지 않았다. 부족하면 재작성기만 따로 학습할 수 있다.
- **LangChain 사용 여부** — 재작성 → 검색 → 생성을 LCEL로 묶을지, 직접 짤지.
- **업무특화 모드가 쓸 어댑터** — 현재 `rag-1_4811건`은 구어체 질문 97문항 중 36건을 거절한다. FAQ 재생성·재학습 후 교체 예정이다. UI는 어댑터 경로를 설정값으로 뺀다.
