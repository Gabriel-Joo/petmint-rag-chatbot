### 1. 설계 원칙

#### 1-1. 모델이 추론할 필요를 UI에서 없앤다

01~06번 전체를 관통한 원칙을 UI까지 끌고 온다.

```
강아지/고양이 구분   → 모델이 추론하지 않고 고객 정보에서 확정
등급(고급/기본/실속)  → 모델이 추론하지 않고 가입 정보에서 확정
유형(Ⅰ/Ⅱ/Ⅲ)       → 모델이 추론하지 않고 가입 정보에서 확정
```

이 셋은 모두 Milvus 메타데이터 필터로 직결된다. UI에서 확정하면 검색 후보에 다른 등급·유형이 애초에 들어오지 못한다.

> **2026-10-14 평가가 이 원칙을 역으로 확증했다.** 질문에 등급 어구가 들어가면 파인튜닝 모델의 거절률이 크게 오른다(등급 언급 문항 15/19 거절). 추론 단계에서 보정하려는 두 실험이 모두 실패했다 — 발췌에 공통 적용 표기를 추가(15건 중 1건 해소, 대조군이 오히려 7건 해소)해도, 질문에서 등급 어구를 제거(15건 중 3건 해소, 새 거절 2건)해도 풀리지 않았다. **등급이 프롬프트에 들어간 뒤에는 되돌릴 방법이 없다.** UI에서 애초에 들어가지 않게 하는 것이 유일하게 작동하는 설계다.
> 

#### 1-2. 상담 업무 흐름을 그대로 반영한다

실무에서는 고객이 전화하면 번호로 조회돼 가입 정보가 먼저 뜬다. "사용자가 종을 고른다"가 아니라 "고객 데이터가 조건을 정한다"가 실제 순서다.

그래서 UI도 `고객 조회 → 상담` 순으로 간다. 이 설계가 1-1의 필터를 자동으로 채워준다.

#### 1-3. 상담 한 건 = 세션 하나

1:1 상담이므로 대화 중에 고객이 바뀌지 않는다. 상담이 끝나면 세션을 닫고 고객 조회로 돌아간다.

세션 단위로 로그가 묶이면 "이 상담에서 무엇을 물었고 어떻게 답했나"가 한 덩어리로 남아 품질 분석에 쓸 수 있다.

### 2. 화면 흐름

```
┌─ 1. 모드 선택 ─────────────────────┐
│  캐릭터 3개                          │
│  일반 / 사내규정 / 업무특화            │
└───────────────────────────────────┘
              ↓ 업무특화
┌─ 2. 고객 조회 ─────────────────────┐
│  카드 3종                            │
│  둘 다 보유 / 한 종만 / 가입 상담      │
└───────────────────────────────────┘
              ↓
┌─ 3. 상담 ──────────────────────────┐
│ 상단  고객·반려동물 정보, 모드, 상담 종료 │
│ 본문  대화          │  근거 조항 패널    │
│ 하단  입력창 (+ 종 토글)               │
└───────────────────────────────────┘
              ↓ 상담 종료
         2번으로 복귀
```

#### 2-1. 모드 선택 — 캐릭터

세 모드의 차이를 설명문 대신 캐릭터 소개로 전달한다.

| 모드 | 소개 | 구성 |
| --- | --- | --- |
| 일반 | "약관은 모르지만 뭐든 물어보세요. 외부로 나가지 않아요" | Tri-7B 원본 |
| 사내규정 | "인사·복무 규정은 제가 알아요" | Tri-7B 원본 + 인사규정 RAG |
| 업무특화 | "펫보험 약관은 제 전문이에요. 근거 조항까지 찾아드려요" | Tri-7B 파인튜닝 + 약관 RAG |

캐릭터는 이 화면에만 크게 나온다. 상담 중에는 작은 아이콘으로 현재 모드만 표시한다 — 고객 전화를 받으며 쓰는 도구라 산만하면 안 된다.

구현은 이모지와 CSS로 시작한다. 그림은 교체 가능한 자원이라 구조에 영향을 주지 않으므로 마지막에 한다.

#### 2-2. 고객 조회 — 카드 3종

| 카드 | 상황 | 상담 화면에서 |
| --- | --- | --- |
| 둘 다 보유 | 강아지·고양이 모두 가입 | 종 토글 표시 |
| 한 종만 | 강아지 또는 고양이만 | 종 고정 |
| 가입 상담 | 비가입자, 신규 문의 | 종만 선택, 등급·유형 필터 없음 |

**"가입 상담"이 중요한 이유**: 콜센터에는 보장 문의만큼 가입 문의가 들어온다. 이 경우 등급·유형이 아직 없으므로 필터 없이 검색하고 전 등급·유형을 보여주는 게 오히려 정확하다.

```
가입자   "제 보험으로 수술비 얼마 나와요?"  → 특정 등급·유형의 답
비가입자  "수술비는 얼마까지 보장되나요?"   → 고급형 200 / 기본형 150 전체 안내
```

비가입자의 전 등급 안내는 검색이 아니라 한도표에서 바로 그린다. `top_k=3`으로는 18개 조합을 다 가져올 수 없기 때문이다.

**가입 상담 카드는 나이를 받는다.** 실속형만 가입 연령이 만 10세까지라(일반조항 제2조), 나이에 따라 안내할 수 있는 등급이 달라진다.

> **가입 심사 질문은 범위 밖이다.** "기왕증이 있는데 가입되나요" 같은 질문은 인수지침·수의사 소견이 필요하고 약관에 기준이 없다. 가입 상담 카드는 **보장 범위 안내**까지만 담당하며, 심사 문의는 거절 응답으로 처리한다. (실제 보험사 FAQ 확인 결과 이런 질문이 상당수이므로, 인수지침을 별도 코퍼스로 추가하는 것은 사내규정 모드와 같은 구조로 확장 가능하다.)
> 

#### 2-3. 상담 화면

**근거 조항 패널**

| 환경 | 배치 |
| --- | --- |
| PC | 본문 오른쪽 2단 패널 |
| 모바일 | 답변 아래 접힌 영역, 탭하면 펼침 |

같은 데이터를 배치만 다르게 한다. 조항을 클릭하면 원문 전문을 보여준다.

**종 토글**은 "둘 다 보유" 고객일 때만 입력창 옆에 나타난다.

**계산 카드**: 치료비가 들어간 질문에는 `limit_table.calculate_payout` 결과를 답변 옆 카드로 보여준다. 모델은 계산에 손대지 않는다(07번 5절 참고).

**부담보 배너**: 가입한 특약에 부담보(예: 슬개골 탈구 제외)가 있고 질문이 거기 해당하면, 코드가 대조해 경고를 띄운다. 모델에게 맡기지 않는 이유는 7B가 예외·단서 추론에서 가장 많이 틀리기 때문이다.

### 3. 검색 필터 — 설계 검토에서 발견한 결함

**상태: 구현 완료.** 회귀 세트 93문항으로 56/87 → 75/87, MRR 0.569 → 0.677 확인. 아래는 발견 경위와 설계 근거 기록.

#### 3-1. 지금 구조에 UI 필터를 그대로 넣으면 검색이 망가진다

`search_engine.py`는 등급·유형 필터를 컬렉션 전체에 건다.

python

```python
coverage_type == "고급형" and type == "Ⅱ"
```

그런데 **의료비 특약 밖의 청크는 전부 `coverage_type`이 null이다.**

```
보통약관 164건
일반조항 85 + 54건
별표·안내·법규
→ 강아지 928건 중 약 750건
```

Milvus에서 `coverage_type == "고급형"`은 null 행을 통과시키지 않는다. BM25 쪽도 마찬가지다. 의료비 특약 안에서도 등급 없는 행이 섹션마다 8~13건 있다(제2조 이후 조문).

**결과**: 고급형Ⅱ 가입자가 "계약 해지하면 환급금 있나요?"를 물으면 보통약관이 한 건도 안 나오고 의료비 특약 제1조만 돌아온다.

**지금 안 드러난 이유**: 질문에 "고급형"을 직접 쓸 때만 필터가 켜진다. UI가 가입 정보로 항상 필터를 채우면 바로 터진다. 02번의 "고급형 6유형 검출 12/12"는 한도 질문만 측정한 결과라 이 결함이 잡히지 않았다.

#### 3-2. 올바른 필터 의미

```
"가입하지 않은 특약·등급만 빼고 나머지는 전부 남긴다"
```

```
(의료비 특약이 아닌 청크는 전부 통과)
or (가입한 의료비 특약 and (내 등급 or 등급 없음))
```

`type`은 `section_name`이 이미 정하므로 따로 필터할 필요가 없다. 가입하지 않은 의료비 특약(예: 통원Ⅲ)은 통째로 빠진다.

> "여섯 유형이 모두 검색된다"(02번 6-6절)는 전제는 **가입 상담에서만** 성립한다. 가입자는 자기가 가입한 유형만 본다.
> 

#### 3-3. SearchScope — 필터를 값 객체로

필터를 문자열 정규식이 아니라 값 객체로 넘긴다. Milvus 식과 BM25 술어를 한 객체에서 만들어야 둘이 엇갈리지 않는다. 지금은 같은 조건을 두 곳에 손으로 따로 쓰고 있다.

```
data/search_scope.py (신규)

Subscription   section_name, coverage_type
SearchScope    species, subscriptions, focus_sections
               milvus_expr()  → Milvus 필터식
               allows(chunk)  → BM25 후보 필터, 같은 의미
               from_query()   → 기존 정규식 동작 (04번 측정 재현용)
```

`data/`에 두는 이유는 08번 Ragas 평가도 서비스와 같은 필터를 써야 하기 때문이다.

기존 `_extract_*_filter`는 지우지 않고 `from_query`로 옮긴다. 04번 측정을 같은 결과로 재현할 수 있어야 한다. 앱에서는 정규식을 **가정 질문 감지기**로만 쓴다.

**함께 바꿀 곳**: `rag_context.search_with_graph`, `build_full_context`, 04번 노트북 셀 2.

**검증**: 모든 청크에서 `scope.allows()` 개수와 Milvus `query(filter=scope.milvus_expr())` 개수가 같은지 확인한다.

#### 3-4. 참조 조문에도 등급 힌트를 준다

등급 없는 청크(예: 의료비 제4조)가 제1조를 참조하면, 지금은 3등급을 `{고급형: X / 기본형: Y / 실속형: Z}`로 병기한다. 가입자라면 자기 등급 한 벌만 붙인다.

컨텍스트가 짧아지고, 다른 등급 숫자를 섞어 말할 여지도 없어진다.

### 4. 되묻기 — 조건을 다시 정의한다

필터가 걸리면 등급·유형은 섞일 수 없다. 남는 애매함은 **통원과 입원 사이**에서 생긴다.

그런데 `limit_table`을 보면 Ⅰ·Ⅱ·Ⅲ 한도는 통원과 입원이 같다. 그래서 조건은 이렇게 된다.

```
발동    상위 결과의 section_name들이 서로 다른 (유형, 등급) 조합에 대응할 때
안 함   같은 등급이면 통원/입원을 물을 필요가 없다
안 함   가입 상담 — 끄고 전 등급을 안내한다. 그러지 않으면 매번 뜬다
안 함   가정 질문 — 질문에 쓴 쪽으로 검색하고 "가입 계약 기준 아님" 배너를 띄운다
```

### 5. 멀티턴 — 백엔드에서 처리한다

"그럼 입원은요?" 같은 후속 질문은 그대로는 검색이 안 된다.

**대화 이력을 프롬프트에 넣지 않는다.** 학습 데이터가 전부 2턴(`system`, `user`)이라 형식이 달라지면 재학습이 필요하다(07번 6절).

| 방법 | 내용 |
| --- | --- |
| 질문 재작성 | 이력 + 후속 질문 → 독립 질문. 모델에는 완성된 질문 하나만 간다 |
| 앞 턴 발췌 이월 | 직전 턴의 상위 발췌를 이번 발췌 목록에 추가. 형식이 그대로라 학습 형식을 안 깬다 |

**재작성기는 베이스 모델을 쓴다.** 파인튜닝 모델은 "발췌를 읽고 상담 말투로 답하기"만 배우므로, 재작성을 시키면 질문을 다시 쓰지 않고 답을 해버릴 가능성이 크다.

**재작성된 질문을 화면에 보여준다.** 상담원이 "내 질문이 저렇게 해석됐구나"를 알 수 있고, 틀렸으면 바로 고쳐 물을 수 있다.

```
┌──────────────────────────────┐
│ 그럼 입원은요?                 │  ← 상담원이 쓴 것
│   ↳ 고급형 입원 수술 한도는?    │  ← 재작성 (작게)
├──────────────────────────────┤
│ 입원 중 수술한 날의 한도는...    │
└──────────────────────────────┘
```

**"더 짧게", "고객에게 말하듯이 다시"** 같은 고쳐쓰기는 검색 질의 문제가 아니라 직전 답변을 입력으로 받는 다른 작업이다. UI 버튼으로 받아 베이스 모델에 넘긴다. 약관 사실은 이미 직전 답변 안에 있으므로 베이스 모델로도 된다.

**비용**: Ollama가 같은 GPU에서 두 모델을 갈아 끼우는 지연이 생긴다. VRAM 예산을 볼 때 함께 본다.

### 6. 데이터 스키마

#### 6-1. 고객 — 특약 단위로 간다

약관을 확인한 결과, 등급은 특약마다 따로 정의된다. 6개 의료비 특약이 각각 제1조에 고급형·기본형·실속형 블록을 둔다. 한도는 "보험증권에 기재된" 값으로 적혀 있어 특약별로 증권에 들어간다.

다만 **"통원과 입원을 같은 등급으로 가입해야 한다"는 조항도, "다르게 가입할 수 있다"는 조항도 약관에 없다.** 이런 조합 규칙은 상품설명서나 사업방법서에 있고 우리 PDF에는 없다.

가능 여부와 무관하게 특약 단위 스키마로 확정한다. 구조가 더 일반적이기 때문이다.

```json
{
  "customer_id": "C001",
  "name": "김보호",
  "phone": "010-1234-5678",
  "pets": [
    {
      "pet_id": "P001",
      "name": "초코",
      "species": "강아지",
      "breed": "포메라니안",
      "age": 3,
      "policies": [
        {
          "section_name": "펫퍼민트 반려견 통원의료비Ⅱ보장 특별약관",
          "coverage_type": "고급형",
          "copay": 30000,
          "contract_date": "2025-03-01",
          "renewal": null
        },
        {
          "section_name": "반려동물 특정 질병 보장제한부 인수 특별약관",
          "excluded_conditions": ["슬개골 탈구"]
        }
      ]
    }
  ]
}
```

| 필드 | 쓰임 |
| --- | --- |
| section_name | 검색 필터. 청크의 section_name과 같은 문자열이어야 한다 |
| coverage_type | 검색 필터 + 계산 카드 |
| copay | 자기부담금 3만/5만. 계산 카드 |
| contract_date | 보장개시·면책기간 판단 (의료비 제1조 30일·1년 단서) |
| excluded_conditions | 부담보. 코드가 질문과 대조해 배너 |

`type`은 담지 않고 `section_name`에서 계산한다. 값을 두 곳에 두면 어긋날 수 있다.

**로더가 검증한다.** `section_name`이 실제 청크에 있는 값인지 확인하고, 하나라도 어긋나면 기동을 실패시킨다. 오타가 나면 필터가 조용히 0건이 되기 때문이다.

**샘플 고객 10명 중 1~2명은 통원·입원 등급을 다르게 넣는다.** 실제로 불가능한 조합이라도 구조가 처리할 수 있는지 시험하는 용도다.

#### 6-2. 세션

```json
{
  "session_id": "uuid",
  "mode": "업무특화",
  "customer_id": "C001",
  "started_at": "...",
  "messages": []
}
```

`pet_id`는 메시지에만 담고 세션에는 두지 않는다. 두 곳에 두면 종 토글과 질문 사이에 값이 엇갈릴 수 있다. 서버는 메시지의 `pet_id`가 세션 고객의 것인지 검증하고 기록한다.

**세션 수명**: 메모리에 두므로 재시작하면 사라진다. WS 재연결 시 4404를 받으면 고객 조회로 돌아간다. 30분 무활동이면 정리한다.

**보존**: 세션 메모리(대화 문맥)는 종료 시 지운다. 로그는 남긴다. 둘을 분리하면 "지운다/남긴다"가 충돌하지 않는다.

#### 6-3. 로그

```json
{
  "turn_id": "uuid",
  "session_id": "uuid",
  "customer_id": "C001",
  "pet_id": "P001",
  "agent": "...",
  "mode": "업무특화",
  "scope": { },
  "hypothetical": false,
  "question": "...",
  "rewritten_question": "...",
  "answer": "...",
  "retrieved": [{"graph_key": "...", "score": 0.72, "content": "..."}],
  "used_references": [ ],
  "clarified": false,
  "model": "...",
  "prompt_version": "rag-1",
  "index_version": "...",
  "first_token_ms": 480,
  "latency_ms": 2300,
  "status": "ok",
  "timestamp": "..."
}
```

**`turn_id`가 필요한 이유**: 피드백 버튼이 가리킬 대상이 있어야 한다. 모든 서버 메시지와 로그에 넣는다.

**`retrieved`에 본문까지 남기는 이유**: 08번 Ragas는 질문·답변·컨텍스트가 모두 필요하다. 키는 `rag_context.graph_key`를 쓴다 — Milvus auto_id는 재색인하면 바뀌므로 쓰지 않는다.

**`prompt_version`·`index_version`**: 이 값이 없으면 로그를 나중에 비교할 수 없다.

**전화번호와 이름은 로그에 넣지 않는다.** `customer_id`만 남긴다.

**피드백**은 `logs/feedback/*.jsonl`에 `turn_id`를 키로 따로 쓴다. 원본 로그는 고치지 않는다.

### 7. API 설계

#### 7-1. REST

```
GET    /api/customers              고객 목록
GET    /api/customers/{id}         고객 상세
POST   /api/sessions               세션 시작 (mode, customer_id)
DELETE /api/sessions/{id}          상담 종료
GET    /api/articles/{species}/{section}/{section_name}/{article_num}
POST   /api/turns/{turn_id}/feedback
```

조항 원문 API에 Milvus id를 쓰지 않는다. 재색인하면 바뀌기 때문이다. 구조 경로로 받아 `ContextBuilder.fetch_article_content`를 그대로 쓴다.

#### 7-2. WebSocket

```
/ws/chat/{session_id}

클라이언트 → 서버
  {"type": "question", "text": "...", "pet_id": "P001"}
  {"type": "cancel"}
  {"type": "clarify_answer", "turn_id": "...", "choice": "..."}

서버 → 클라이언트
  {"type": "sources", "turn_id": "...", "items": [...]}      검색 결과 (생성 전)
  {"type": "token", "turn_id": "...", "text": "..."}         스트리밍
  {"type": "clarify", "turn_id": "...", "options": [...]}    되묻기
  {"type": "references", "turn_id": "...", "items": [...]}   실제 쓴 근거
  {"type": "done", "turn_id": "...", "latency_ms": 2300, "first_token_ms": 480}
```

**`sources`를 먼저 보내는 이유**: 검색 결과는 생성 전에 이미 나와 있다. 먼저 보내면 근거 패널이 0.5초 안에 찬다. 답변이 실제로 쓴 것(`used_references`)은 생성이 끝나야 알 수 있으므로 나중에 `references`로 보낸다.

**`cancel`을 처음부터 넣는다**: 생성 중에 새 질문이 오거나 상담이 끝나면 Ollama 스트림을 취소해야 한다.

**스트리밍을 쓰는 이유**: 7B가 500자를 만들면 5~10초다. 통째로 기다리면 빈 화면이고, 흘려보내면 0.5초 만에 첫 글자가 나온다. 같은 10초인데 체감이 다르다.

#### 7-3. 프로세스 모델

**GPU를 쓰는 것은 전부 호스트에 두고, Pod는 네트워크로 호출한다.**

GPU 패스스루를 하지 않기로 했으므로 K8s Pod에서는 GPU를 쓸 수 없다. 그런데 이 서비스는 GPU를 두 곳에서 쓴다 — 검색(KURE 임베딩 + bge-reranker)과 생성(Ollama)이다. 생성은 이미 호스트 Ollama를 호출하는 구조이므로, 검색도 같은 방식으로 호스트 서비스로 빼낸다.

```
[GPU 호스트]
  Ollama           :11434   생성
  search-service            KURE + bge-reranker + Milvus 조회
       ↑ 네트워크 호출
[K8s Pod]
  FastAPI 앱               세션·필터·계산·조립 (GPU 미사용)
```

| 대안 | 기각 이유 |
| --- | --- |
| 검색을 Pod에서 CPU로 | 리랭커가 후보를 쌍으로 비교하는 구조라 지연이 크게 늘어난다 |
| Pod에 GPU 할당 | 패스스루를 하지 않기로 한 결정과 충돌한다 |

**얻는 것**: 검색 모델이 앱 프로세스에서 빠지므로 uvicorn worker 수를 제한할 이유가 없어진다. 세션 저장소만 공유하면(또는 sticky session) worker를 늘려 동시 접속 여력을 키울 수 있다.

`engine.search`는 동기 함수이고 GPU를 쓰므로, 한 번에 하나씩 실행하는 직렬화는 search-service 안에서 한다. 앱은 HTTP를 비동기로 호출할 뿐이라 이벤트 루프가 막히지 않는다.

**개발 중에는 분리하지 않는다.** `data/search_engine.py`는 그대로 두고, 그것을 감싸는 얇은 HTTP 래퍼만 따로 둔다. 노트북 01~08은 지금처럼 직접 import하고 서비스만 HTTP로 호출한다 — 평가와 서비스가 같은 코드를 쓰는 원칙(3-3절)이 깨지지 않는다.

**VRAM 예산을 계산해야 한다.** 호스트 GPU(RTX 5070 Ti, 16GB) 하나를 Ollama와 search-service가 나눠 쓴다.

| 모델 | 상주 방식 | VRAM |
| --- | --- | --- |
| KURE-v1 임베딩 (fp32, 현재 `SearchEngine` 기본값) | search-service 상시 상주 | 실측 후 확정 |
| bge-reranker-v2-m3 (fp16, max_length 1024) | search-service 상시 상주 | 실측 후 확정 |
| Tri-7B 원본 (Q4_K_M GGUF) | Ollama, 갈아 끼움 | 실측 후 확정 |
| Tri-7B 파인튜닝 (Q4_K_M GGUF) | Ollama, 갈아 끼움 | 실측 후 확정 |

**검색 모델 몫을 먼저 뺀다.** 검색 모델 둘은 상시 상주이고 Ollama 모델만 갈아 끼우는 구조다. 따라서 Ollama가 쓸 수 있는 예산은 `16GB − (KURE + 리랭커 + 리랭커 추론 피크)`이고, `OLLAMA_MAX_LOADED_MODELS`와 `keep_alive`는 이 남은 몫으로 정한다. 리랭커는 배치 추론 중 활성화 메모리가 늘어나므로 적재 직후가 아니라 검색 실행 중 피크로 잡는다.

**모드 전환 시 Ollama 모델 두 개가 동시에 올라갈 수 있는가.** 재작성기는 베이스 모델(= Tri-7B 원본)이므로 업무특화 모드는 한 턴 안에서 원본(재작성) → 파인튜닝(답변)을 오간다. 그래서 이 판단은 모드 전환 때만이 아니라 업무특화 턴마다 걸린다.

```
남은 예산 ≥ 원본 + 파인튜닝 (+ 각 KV 캐시)  → OLLAMA_MAX_LOADED_MODELS=2, 둘 다 상주
남은 예산 <  원본 + 파인튜닝               → 1로 두고 턴마다 스왑. 스왑 지연을 first_token_ms로 측정
```

**측정 방법**

```
# search-service 프로세스 VRAM (모델 적재 후, 검색 몇 건 실행 후 각각)
nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv
# search-service 안에서 리랭커 피크
torch.cuda.max_memory_allocated()   # 검색 실행 후

# Ollama 모델별 적재 크기 (각 모델로 1회 생성 후)
docker exec ollama ollama ps
# 전체 여유
nvidia-smi --query-gpu=memory.used,memory.total --format=csv
```

**재부팅 대응**: Ollama 컨테이너가 `restart=no`다. systemd 유닛에 Ollama·Milvus 의존성을 넣거나 재시작 정책을 바꿔야 한다.

K8s 배포 후에는 systemd 대신 Deployment와 probe가 이 역할을 한다. Ollama는 GPU 호스트에 그대로 두고 Pod가 네트워크로 호출하므로(GPU 패스스루를 하지 않기로 한 결정), 컨테이너화 대상은 FastAPI 앱과 React 빌드물뿐이다.

> **파인튜닝 모델은 GGUF 변환이 필요하다.**
> 

> LoRA 어댑터 + 베이스 병합 → GGUF 변환(llama.cpp) → 양자화 → Modelfile → ollama create
> 

> **양자화를 베이스와 같은 Q4_K_M으로 맞춘다.** 다르면 모드 간 차이가 파인튜닝 효과인지 양자화 차이인지 구분되지 않는다. 변환 후 97문항 평가를 다시 돌려 양자화로 인한 성능 변화를 확인한다 — 지금까지의 평가는 양자화 전 상태에서 측정한 값이다.
> 

#### 7-4. 인증

Cloudflare Access를 쓴다. 이 화면들은 고객 이름과 전화번호를 보여주므로 터널을 열기 전에 인증이 있어야 한다.

Access는 코드가 0줄이다. 앱은 `Cf-Access-Authenticated-User-Email` 헤더만 읽어 상담원 ID로 로그에 남긴다. 내부망 직접 접속에는 헤더가 없으므로, 내부망도 터널을 거치게 하거나 개발용 기본값을 둔다.

### 9. 정하지 못한 것

- **"사내규정" 모드의 데이터** — 가상 인사규정 전처리 완료(청크 49개, 참조 그래프 7엣지, 회귀 세트 24문항). Milvus 색인만 남았다. 지금 `SearchEngine`은 강아지·고양이 컬렉션을 하드코딩하므로, 모드마다 리트리버가 다르다는 인터페이스를 먼저 뚫어둔다.
- **멀티턴 재작성의 실제 품질** — 재작성이 충분한지 측정하지 않았다. 부족하면 재작성기만 따로 학습할 수 있다(답변 모델 재학습은 아니다).
- **LangChain 사용 여부** — 재작성 → 검색 → 생성을 LCEL로 묶을지, 직접 짤지. 콜백으로 로깅이 깔끔해지는 이점이 있다.
- **업무특화 모드가 쓸 어댑터** — 현재 `rag-1_4811건`은 구어체 질문 97문항 중 36건을 거절한다. FAQ 재생성·재학습 후 교체 예정이다. UI는 어댑터 경로를 설정값으로 빼 모델만 갈아끼울 수 있게 만든다.
