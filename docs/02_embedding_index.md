### 1. 왜 벡터 DB를 쓰는가

전통적인 키워드 검색(SQL의 LIKE, Elasticsearch의 BM25 등)은 "글자가 동일한지"를 기준으로 찾는다. 사용자가 "강아지가 아파서 병원 갔는데 돈 돌려받을 수 있나요?"라고 물으면, 약관에는 "통원의료비", "보험금의 지급사유" 같은 단어가 쓰여 있지 "돈 돌려받다"라는 표현 자체는 없어서 키워드 검색으로는 못 찾는다.

벡터 검색은 문장을 "의미를 담은 숫자 벡터"로 바꿔서, 글자가 같은지가 아니라 **의미가 비슷한지**로 비교한다. "돈 돌려받다"와 "보험금 지급"은 겉보기엔 다른 단어지만 의미상 가까운 벡터로 변환되기 때문에 벡터 검색은 이 둘을 연결해 찾아낼 수 있다.

실제 상담원이나 가입자는 약관의 전문 용어를 그대로 쓰지 않고 일상어로 질문할 가능성이 높다 — "통원 한도가 얼마예요?"가 아니라 "병원비 얼마나 받을 수 있어요?" 같은 식으로. 키워드 검색만으로는 이런 표현의 차이를 넘어서지 못한다.

**전용 저장소가 필요한 이유**: 이 벡터는 숫자가 1024개(KURE-v1 기준)씩 들어있는 긴 배열이다. 수백~수천 개의 청크마다 이런 벡터가 있으면 "가장 비슷한 벡터를 빠르게 찾는" 전용 인덱스 구조가 필요하다. 일반 DB는 벡터 간 유사도 검색에 최적화돼 있지 않아 Milvus 같은 전용 벡터 DB를 썼다.

### 2. 왜 Milvus인가 (Chroma에서 전환)

처음엔 Chroma로 시작했다. 설치와 사용이 간단해 로컬 프로토타이핑에 적합한 벡터 DB다. 하지만 이 프로젝트는 "사내 LLM 서비스로 실제 배포 가능한 수준"을 목표로 하고 있어서, 프로덕션급 벡터 DB 경험을 쌓는 쪽으로 Milvus를 선택했다.

Milvus의 차별점:

- **다양한 인덱스 타입**(HNSW, IVF 등) — 데이터 규모와 성능 요구에 따라 전략을 바꿀 수 있다
- **분산 처리·스케일링 전제 아키텍처** — 데이터나 트래픽이 늘어도 구조적으로 대응 가능하다
- **메타데이터 필터링과 벡터 검색의 결합** — "강아지/고양이로 나누고, section·조 번호로 걸러내야 하는" 이 프로젝트의 요구에 잘 맞았다

실제로 이 프로젝트는 1인 개발·로컬 서버·수천 건 수준이라 Chroma로도 돌아간다. 다만 "실제 서비스로 배포한다"는 목표를 생각하면 지금부터 프로덕션 지향 도구에 익숙해지는 게 낫다고 판단했다.

**임베딩 — KURE-v1**

고려대 NLP&AI 연구실이 bge-m3를 한국어 query-document 쌍 200만 건으로 추가 학습한 모델이다. 기반이 같으므로 1024차원·8192토큰을 그대로 물려받고, 한국어 검색에서 기반 모델보다 낫다(MTEB-ko 검색 평균 80.76 대 79.30). MIT 라이선스라 상업 이용에 걸림이 없다. 8192토큰은 이 프로젝트에 넉넉하다 — 가장 긴 청크가 4,940B다. 리랭커는 같은 계열의 bge-reranker-v2-m3를 쓴다. 임베딩과 기반이 같아 결과가 어긋날 여지가 적다.

### 3. 왜 강아지/고양이 컬렉션을 분리했나

**대안**: 하나의 컬렉션에 다 넣고 `species` 메타데이터로 필터링하는 방식도 가능했다.

**분리를 선택한 이유**: UI 설계상 사용자가 먼저 강아지/고양이를 선택하므로, 검색 시점에 이미 종이 확정돼 있다.

- 컬렉션을 분리하면 검색 자체가 그 종의 컬렉션 안에서만 이뤄져, 다른 종의 데이터가 섞일 가능성이 **구조적으로 차단**된다
- 하나의 컬렉션에 넣고 필터링하면, 코드가 필터를 빠뜨리는 실수를 할 여지가 생긴다

즉 검색 정확도뿐 아니라 "실수를 원천 차단하는 안전장치" 설계였다. 강아지/고양이는 특약 구성 자체가 다르다는 걸 01번에서 확인했기 때문에 둘을 섞으면 안 되는 이유가 명확했다.

**인사규정은 별도 컬렉션이다.** `hr_regulation`에 담고 스키마도 다르다 — 등급·유형·특약이 없는 문서라 그 필드들을 두지 않는다. 같은 `SearchEngine`을 쓰되 코퍼스 이름으로만 갈린다(`hr_index.py`).

#### 3-1. 인사규정 개정 반영 — 제25조 ① 지급일(2026-10-28)

"매월 1일부터 말일까지를 산정기간으로 하여 **당월 25일**에 지급한다"는 산정기간이 끝나기 전에 지급하는 셈이라 "**익월 10일**에 지급한다"로 고쳤다. ②항(휴일이면 전일)은 그대로다.

**원본.** `data/raw_pdf/펫퍼민트손해보험_인사규정.pdf`(10쪽, LibreOffice 24.2 Writer로 내보낸 PDF). Writer 원본(.odt/.docx)은 이 머신에 없고 LibreOffice도 설치돼 있지 않다. 전처리(`data/hr_preprocess.py`)는 PDF를 읽으므로 PDF가 원천이다. PDF·청크는 git 밖(.gitignore)이라 고치기 전 원본과 청크·그래프 8벌을 `backups/hr_regulation_art25_20261028/`에 두었다(되돌리기는 같은 폴더 `ROLLBACK.md`).

**고친 방법 — PDF 내용 스트림의 글자 코드만 바꾼다.**
- 처음엔 세 글자를 지우고(redact) 새로 써 넣었다. 그림은 맞았지만 새 글자가 쪽 내용의 맨 끝에 붙어, 추출하면 "…하여 / 월 / 일에 지급한다." 뒤에 "익 10"이 따로 나왔다. 전처리는 내용 순서(`sort=False`)를 따르므로 청크가 깨진다 → 버렸다
- 대신 5쪽 내용 스트림에서 그 줄의 텍스트 연산자를 직접 고쳤다. '당'(F3 `A1`)이 든 `TJ`를 그 앞에서 끊고 같은 글꼴의 다른 부분집합(F5)에 이미 있는 '익'(`2B`, 7·10쪽 "이익"·"불이익"에 쓰인 글리프)을 넣은 뒤 F3로 돌아간다. "25"(DejaVu F4 `0B0F`)는 같은 부분집합의 "10"(`0A12`)으로. 전각 한글·같은 폭 숫자라 위치가 그대로다
- 확인: 10쪽 추출 글자 중 바뀐 것은 그 세 글자뿐(같은 위치), 다시 만든 청크 49개 중 바뀐 칸은 제25조 content 하나, 그래프는 같다

**반영.** 청크·그래프를 로컬 4벌(기본·v2·v3·v4)과 NFS(같은 저장소)에 → `python -m data.hr_index`(Milvus `hr_regulation` 재적재 — 적재 직후 행을 세던 검사가 0행으로 나와 실패처럼 보였다. flush·강한 일관성으로 고쳤다) → search-service 재시작(BM25를 기동 때 만든다). 운영 앱은 청크를 기동 때 읽으므로 Pod가 다시 떠야 새 본문이 근거 패널·발췌에 나온다.

**회귀.** 인사규정 검색 회귀 기존 24문항 순위·상위 3 그대로 + 새 2문항(H025 월급 지급일·H026 휴일) 1위. 약관 103문항 순위 그대로(80·97·97 / MRR 0.897). 사내규정 답 프롬프트 38개 중 바뀐 것은 발췌에 제25조가 든 HR13 하나(답의 결론 같음). "10월분 급여는 언제?" → 11월 10일.

**다른 조항과의 관계(고치지 않음).**
- 제45조 ② 퇴직일부터 14일 이내 금품 청산 — 퇴직자는 이것이 지급일보다 먼저다(예: 10월 15일 퇴직 → 10월 29일까지, 정기 지급일 11월 10일 전). 특칙이지 충돌은 아니다
- 제3조 4호 평균임금 = 이전 3개월 동안 **지급된** 임금 — 익월 10일 지급이므로 그 달 급여는 다음 달 10일부터 '지급된' 것이다. 개인화 계산(`hr_personal.paid_by`)을 이 기준으로 맞췄다(매달 1~9일에만 달라진다)

### 4. 스키마 설정

```
id                  INT64                기본키, auto_id
vector              FLOAT_VECTOR(1024)   KURE-v1 임베딩
content             VARCHAR(12000)
species             VARCHAR(10)
section             VARCHAR(64)
section_name        VARCHAR(256)
type                VARCHAR(5)           Ⅰ/Ⅱ/Ⅲ
article_num         INT64
article_title       VARCHAR(256)
coverage_type       VARCHAR(10)          고급형/기본형/실속형
paragraph_num       INT64
chunk_index         INT64
chunk_total         INT64
context_prefix      VARCHAR(1024)              분할된 뒷조각의 맥락
printed_page_start  INT64
printed_page_end    INT64
citations_raw       VARCHAR(4000)
```

메타 필드는 nullable이고 `enable_dynamic_field=True`다.

**AUTOINDEX + COSINE**: 데이터 규모가 작은 단계라 Milvus 자동 선택 인덱스로 충분했고, COSINE은 문장 임베딩 비교에서 일반적으로 쓰이는 거리 측정 방식이다.

**VARCHAR 길이는 실측으로 정했다**: Milvus의 `max_length`는 **바이트 기준**이라 한글은 글자당 3바이트다. 처음에 `section`을 20으로 잡았는데 `"기타_제도성_특별약관"`이 29바이트라 삽입이 실패할 수 있었다. 실제 데이터의 최대 바이트를 전부 재서 여유를 두고 다시 잡았다.

```
section         29 bytes  → 64
section_name    67 bytes  → 256
article_title   83 bytes  → 256
citations_raw  797 bytes  → 4000
content       4940 bytes  → 12000
```

### 5. 1차 검증 — 검색 동작 확인

"통원 한도가 얼마인가요?" 질문으로 검색했을 때 상위 결과가 "안내_요약"(약관 요약서)으로 쏠렸다. 요약서가 "보장명/보장한도" 형식의 간결한 표라 질문과 표면적으로 더 유사하게 매칭된 것이다.

검색 엔진 자체의 오류라기보다 section별 우선순위를 검색 로직에서 조정해야 한다는 신호였다. 이 **"짧고 간결한 텍스트가 실제로는 덜 유용한데도 검색 점수가 높게 나오는"** 현상은 이후 6절에서 훨씬 심각한 형태로 재발했다.

### 6. 검색 아키텍처 재설계

#### 6-1. 짧은 청크가 핵심 정보보다 높은 점수를 받는 문제

01번에서 `type` 필드를 추가한 뒤 "고급형 수술 한도가 얼마인가요?"로 재검증했다. 그런데 상위권이 **"① 고급형"처럼 조문 제목 한 줄만 담긴 청크**로 채워지고, 정작 "1일당 200만원"이 담긴 한도표 청크는 10위 안에도 들지 못했다.

코사인 유사도를 직접 계산해보니:

```
"① 고급형" (쿼리와 거의 동일한 짧은 단어)    0.618
실제 정답 청크 (700자 가까운 표+설명)        0.447
```

원인을 더 파보니, `coverage_type`이 메타데이터 필드로는 존재하지만 **청크 본문 텍스트 안에는 그 단어가 없었다**. 01번의 등급 분리 로직이 "① 고급형"을 구분자로만 쓰고 본문에 다시 넣지 않았기 때문이다. 임베딩 모델은 긴 한도표 청크가 "고급형에 관한 것"이라는 사실 자체를 알 길이 없었고, 반대로 그 단어만 담은 짧은 청크가 어휘적으로 일치해 역설적으로 더 높은 점수를 받았다.

#### 6-2. 1차 완화 — 임베딩 텍스트에 메타데이터 헤더 보강

`content`는 원본 그대로 두되(사용자에게 보여줄 때 깨끗해야 하므로), **임베딩을 생성하는 텍스트만** 별도로 만들어 `section_name`·`type`·`coverage_type`·`article_title`을 헤더로 붙였다.

```
[펫퍼민트 반려견 통원의료비Ⅲ보장 특별약관 / 유형Ⅲ / 고급형 / 보험금의 지급사유]
[1. 눈의 장해 > 나. 장해판정기준]
회사가 보상하는 비용은 각 항목별 피보험자가 부담한...
```

유사도 격차는 줄었으나(0.447→0.455, "① 고급형"도 0.618→0.499로 하락) 여전히 짧은 청크가 근소하게 앞섰다 — 임베딩 모델이 텍스트 길이에 따라 신호가 희석되는 경향 자체는 헤더 보강만으로 해결되지 않았다.

#### 6-3. Hybrid Search(BM25+Dense) + Reranker

근본 해결을 위해 세 가지를 순서대로 추가했다.

1. **BM25(키워드 검색)** 를 Dense 검색과 병행했다. BM25는 "고급형", "한도" 같은 정확한 단어 매칭에 강하고 텍스트 길이에 따른 신호 희석이 없다.
2. 그런데 1차 결합만으로는 "수술"처럼 여러 조항에 공통으로 등장하는 단어 때문에 엉뚱한 조항(용어 정의 등)이 끼어들었다. 가중치를 조정해봤지만 한쪽을 누르면 다른 쪽 노이즈가 느는 핑퐁이 이어져, 가중치 튜닝만으로는 한계가 있다고 판단했다.
3. **Reranker**(`BAAI/bge-reranker-v2-m3`, Cross-encoder, Apache 2.0)를 추가해, BM25+Dense로 넉넉히 뽑은 후보를 쿼리와 직접 대조해 재정렬하도록 했다. 이 단계에서 "① 고급형" 같은 초단문 청크가 상위권에서 사라지고 실제 숫자가 담긴 한도표가 상위를 차지하기 시작했다.

#### 6-4. 등급·유형 메타데이터 필터

5개 쿼리로 재현성 테스트를 해보니, Hybrid+Reranker만으로는 "고급형을 물었는데 기본형이 1등으로 나오는" 혼동이 남아 있었다 — 아홉 가지(등급×유형) 조합이 거의 동일한 문장 구조를 공유하기 때문에 의미 기반 재정렬만으로는 등급 자체를 구분하지 못했다.

질문에 "기본형/고급형/실속형" 또는 "Ⅰ/Ⅱ/Ⅲ"가 명시돼 있으면 **Milvus 검색 시점에 메타데이터로 강제 필터링**하도록 추가했다. SearchScope가 의료비 특약 범위를 좁힌다. 등급이 비어 있는 청크는 통과시키고, 유형(type)으로는 거르지 않는다. 대신 검색 문장에서 등급 단어를 빼, 등급 때문에 엉뚱한 조항이 올라오는 것을 줄인다.

#### 6-5. 리랭커가 긴 청크의 뒷부분을 못 보던 문제

리랭커를 `max_length=512`로 띄우고 있었는데, 이 문서는 **1글자당 약 0.58토큰**이라 1000자 청크가 580토큰이다. 즉 1000자 청크의 뒷부분은 리랭커가 아예 보지 못한 채 점수를 매기고 있었다.

512와 1024를 같은 조건으로 비교했다. 평가용으로 "512토큰 뒤쪽 내용에서만 답할 수 있는 질의" 85개를 만들고, 대조군으로 짧은 청크 질의 120개를 함께 썼다.

|  | 512 fp32 | 1024 fp32 | 1024 fp16 |
| --- | --- | --- | --- |
| 꼬리 질의 MRR (강아지/고양이) | 0.677 / 0.596 | 0.702 / 0.647 | 0.702 / 0.647 |
| 대조군 (짧은 청크) | 기준 | 동일 | 동일 |
| 고급형 6유형 검출 | 12/12 | 12/12 | 12/12 |
| 평균 / p95 지연 | 443 / 555ms | 623 / 1111ms | **200 / 362ms** |
| 가중치 / 추론 메모리 | 2.27 / 0.75GB | 2.27 / 1.51GB | **1.14 / 0.77GB** |

1024 fp32는 품질이 오르지만 p95 지연이 2배가 됐다. 상담원이 쓰는 도구에서 1초 넘는 지연은 체감되는 수준이라 그대로 채택하기 어려웠다.

그런데 리랭커가 fp32로 돌고 있는 걸 발견하고 fp16으로 바꿔 재측정하니, **품질은 그대로인데 지연이 기존 512 fp32보다 오히려 줄었다**(443→200ms). 메모리도 절반이 됐다. fp32와 fp16의 점수 차는 최대 0.0013이었고, 실제 질문 36건 중 34건은 top-8 순서까지 같았다.

→ **1024 + fp16으로 확정**

> 
> 
> 
> 이 측정에 쓴 꼬리 질의 85개와 대조군 120개는 당시 임시로 만든 것이라 저장소에 남아 있지 않다. 이후 04번 9-1절의 회귀 세트가 그 역할을 대신한다.
> 
> 이 측정은 "512토큰 뒤쪽에서만 답할 수 있는 질의 85개"로 잰 것이다. 이후 04번 9절의 회귀 세트로 다시 재었을 때는 512 → 1024의 차이가 더 작았다(상위 5개 안 74 → 75, MRR 0.657 → 0.677). 세트 성격이 달라서다 — 회귀 세트는 꼬리 질의만 모은 게 아니다. fp16은 두 측정 모두에서 fp32와 순위가 같고 약 3배 빠르다.
> 

#### 6-6. 중복 제거 키가 서로 다른 청크를 덮어쓰던 문제

가장 큰 발견이었다. "고급형 수술 한도가 얼마인가요?"를 물으면 결과가 **전부 통원Ⅲ 고급형**이고 Ⅰ·Ⅱ유형이 하나도 나오지 않았다. 3위 점수는 0.0007로 급락해 사실상 유효 후보가 둘뿐이었다.

원인은 BM25와 Dense 후보를 합칠 때 쓰던 중복 제거 키였다.

```python
candidates[c["content"][:80]] = c   # content 앞 80자를 키로
```

한도표가 든 조항은 등급·유형과 무관하게 전부 같은 문장으로 시작한다.

```
"회사가 보상하는 비용은 각 항목별 피보험자가 부담한 치료비에서..."
```

즉 **통원/입원 × Ⅰ·Ⅱ·Ⅲ 여섯 개 한도표가 전부 같은 키**가 되어 서로 덮어썼고, 마지막에 쓰인 Ⅲ만 살아남았다. 측정해보니 28개 후보가 **6개로 붕괴**했고 22건이 덮어써졌다.

고유 식별자 튜플로 교체했다.

```python
(section, section_name, type, article_num, paragraph_num, coverage_type, chunk_index, content)
```

`chunk_index`는 Milvus 스키마에 없던 필드라 함께 추가하고 재색인했다. `section`과 `type`도 키에 넣어, 같은 이름의 조가 다른 섹션·유형에 있을 때 섞이지 않게 했다. 마지막의 `content`는 6-7절에서 더한 것이다.

**결과**: 후보 6 → 21개로 복원되고, 통원·입원 × Ⅰ·Ⅱ·Ⅲ **여섯 유형이 전부 top-8**에 올라왔다.

```
0.5675 Ⅰ/고급형/통원    0.5160 Ⅱ/고급형/입원
0.5636 Ⅱ/고급형/통원    0.4645 Ⅲ/고급형/통원
0.5233 Ⅰ/고급형/입원    0.4269 Ⅲ/고급형/입원
```

> 이 수정으로 "유형을 특정하지 않은 질문에는 세 유형을 모두 보여주고, UI에서 되묻는다"는 설계가 비로소 가능해졌다. 검색이 한 유형만 가져오면 애초에 "답이 갈린다"는 판단 자체를 할 수 없다.
> 

#### 6-7. 안내류 청크가 뭉개지던 문제

6-6의 키 교체 후에도 문제가 남았다. 안내류(개인정보 안내문, 용어 해설 등) 청크는 `article_num`·`paragraph_num`·`coverage_type`이 전부 `None`이라, 키가 사실상 `(section_name, None, None, None, chunk_index)`로 축퇴한다. 같은 섹션 안의 청크들이 전부 같은 키가 되어 **종당 137개가 12개로 뭉개졌다**.

01번 레코드의 다른 메타 필드(`item_num`, `sub_label`, `top_category`)를 더해봤지만 충돌이 12→7그룹으로 줄 뿐 남았고, 결정적으로 **그 필드들이 Milvus 스키마에 없어서** Dense 쪽 키와 BM25 쪽 키가 달라지는 문제가 있었다.

결국 키에 `content`를 포함하기로 했다. 우려했던 두 가지를 측정으로 확인하고 내린 결정이다.

- **공백 차이**: Milvus의 content와 JSON의 content가 928/850건 모두 완전히 일치(드리프트 0)
- **비용**: 파이썬이 문자열 해시를 캐시하므로 키 하나당 약 0.05µs, 후보 40개 기준 무시할 수준

**결과**: 안내류 질문의 후보 수가 회복됐다(민원 상담 12→35개, 청약철회 21→39개). "고급형 수술 한도"의 6유형 top-8과 순서는 그대로 유지됐다.

#### 6-8. 리랭커 입력이 임베딩과 달랐던 문제

Dense 색인은 6-2의 메타데이터 헤더를 붙여 임베딩했는데, 리랭커에는 **순수 본문만** 넘기고 있었다. 리랭커가 "이게 고급형인지" 알 수 없는 상태로 점수를 매긴 셈이다.

| 질문 | 본문만 (기존) | 헤더 포함 |
| --- | --- | --- |
| 고급형 수술 한도 | 0.0553 → 0.0007 (급락) | 0.4645 → 0.0520 (단계 유지) |
| 통원Ⅱ 기본형 비수술 | 0.5017 → 0.0043 (평탄) | 0.8766 → 0.3938 (분리) |

본문만 주면 한도표가 등급·유형과 무관하게 거의 동일해서 리랭커가 변별하지 못했다. 헤더를 포함하니 점수가 4~170배 커지고 단계적으로 분리됐다. 임베딩·BM25·리랭커가 **같은 표현을 보도록** 통일했다.

#### 6-9. search_engine.py로 모듈화

위 로직(BM25 인덱스 구축, Dense 검색, 메타 필터, 중복 제거, Reranker)을 02번 노트북 안에만 두면 04번이 재사용할 수 없어 같은 버그를 다시 겪는다. `data/search_engine.py`라는 독립 모듈로 분리해, 04번이 SearchEngine을 쓴다. 02번은 build_embedding_text만 가져다 쓰고 Dense 검색만 시험한다.

### 7. 정직한 한계

- **검증 쿼리 수가 적다**. 6-6·6-8은 10개 질문 × 2종으로 측정했다. 더 다양한 질문 패턴(복수 조건 조합, 등급+유형 동시 언급 등)에 대한 검증은 ✓ 04번 9-1절의 회귀 세트 103문항으로 한다. 생성 품질까지 포함한 정량 평가는 △ 08번(Ragas)에서 다룬다.
- **등급·유형을 명시하지 않은 질문**에도 가입 정보로 범위가 정해진다(✓ 09번 3-3절 `SearchScope.for_policies`). 되묻기는 상위 결과가 서로 다른 (유형, 등급) 조합에 걸칠 때만 발동한다(09번 4절, △ 코드 작성(2026-10-18), 실행 확인 전).
- **`content`를 중복 제거 키에 쓰는 것**은 "Milvus와 JSON의 content가 동일하다"는 전제에 의존한다. 지금은 측정으로 확인했지만, 색인 파이프라인이 바뀌면 이 전제를 다시 확인해야 한다.
