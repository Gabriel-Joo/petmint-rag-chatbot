#### 2. 변경 사항 (우선순위 순)

#### 2-1. [1순위] 같은 질문으로 양성·no_answer 쌍을 만든다 — build 단계

**무엇을**: no_answer로 뽑힌 QA마다 같은 질문의 양성 샘플을 하나 더 만든다. 양성 쪽 발췌는 **그 no_answer의 방해 발췌 + gold 발췌**다. 두 샘플의 차이는 gold 발췌가 있느냐 하나뿐이다. 그러면 모델은 질문이 아니라 발췌를 읽어야 라벨을 맞힐 수 있다.

**어디**: `data/finetune_data.py` — `assign_kinds`(종류 배정) 뒤, `build_sample`(샘플 조립).

**정할 것 / 제안**:
- 쌍의 양성은 **추가**한다(기존 distract를 대체하지 않는다). train이 약 +690건(+10%) 늘고, no_answer 비율은 10% → 약 9.2%(690/7,496)가 된다. `--gate-min-no-answer-ratio` 기본값 0.08 안이다.
- meta에 `pair_id`를 두 샘플 모두에 넣는다. 양성 쪽 kind는 `distract_pair`로 따로 둔다. 그래야 `overlap_report`·07 노트북의 종류별 출력에서 따로 보인다.
- gold 위치는 기존 distract와 같은 방식(해시)으로 섞는다. 쌍은 같은 unit이라 val/train 분할(`is_val(unit_id)`)이 자동으로 같다.
- 쌍 양성의 발췌 토큰이 `MAX_LENGTH`를 넘으면 기존 `fit_to_budget` 규칙을 따른다. 버려지면 그 쌍의 no_answer도 버리지 말고 건수만 기록한다.
- no_answer 방해 발췌 판정(`--na-judge=v2`)은 그대로다. 쌍의 양성은 그 판정을 통과한 같은 방해 발췌를 쓴다.

#### 2-2. [2순위] 짧은 구어체 양성 질문을 추가한다 — rewrite 단계

**무엇을**: 재작성에 변형을 하나 더 둔다. 20~35자 고객 말투에, 발췌 원문 어휘를 피하는 질문이다(평가 질문과 같은 성질). 기존 재작성 질문을 바꾸지 않고 **같은 답의 추가 질문**으로 넣는다.

**어디**: `data/faq_rewrite.py` — 프롬프트 변형, 재심판, `export_final`(추가 질문을 별도 행으로). `faq_style`에 길이·겹침 통계 열을 추가한다.

**목표(제안)**: 겹침 0.3 미만 양성을 603건에서 1,500건 이상으로 늘린다. 근거는 다음과 같다. 0.3 미만 no_answer 263건 기준으로 이 구간 NA 비율을 15%(전체의 1.5배) 이하로 맞추려면 양성이 약 1,490건 필요하다. 30자 미만 질문은 2.4%에서 10% 이상으로.

**주의**:
- 재심판(gemma4:12b)을 그대로 통과해야 채택한다. 짧아지면서 조건이 빠지면 `incomplete`로 떨어지는 것이 정상이다.
- 이 변형의 질문도 2-1의 쌍 대상이 될 수 있어야 한다(no_answer 쪽에도 짧은 질문이 들어가야 짧음이 라벨 신호가 되지 않는다).
- 평가 97문항을 few-shot 예시로 쓰지 않는다. 빌드 후 평가 질문이 학습셋에 없는지 검사한다(이번처럼 부분 문자열 검사).

#### 2-3. [3순위] 등급 어구 + 공통 조항 양성을 늘린다 — rewrite(또는 gen) 단계

**무엇을**: 등급과 무관한 조항(gold unit `coverage_type` None)에 "고급형인데…", "Ⅲ유형인데…" 같은 등급·유형 어구가 붙은 질문을 만든다. 이 질문들도 2-1의 쌍에 섞어 no_answer 쪽에도 들어가게 한다.

**어디**: `data/faq_rewrite.py`(질문 앞에 어구를 붙이는 변형) 또는 05 주제 지정 회차. 어구 판정은 `search_scope.mentioned_grade`·`mentioned_type`을 그대로 쓴다.

**규칙**:
- 의료비 특약(`MEDICAL_SECTIONS`)은 유형이 섹션 이름에 박혀 있으므로 **등급만** 붙인다. 유형은 그 섹션의 유형과 같아야 한다. `answer_eval.common_note`가 COMMON_NOTE / COMMON_NOTE_MEDICAL로 나누는 기준과 같다.
- 등급 지정 단위(`coverage_type` 있음)에는 붙이지 않는다. 거기서는 등급이 답을 바꾸는 정보다.

**목표(제안)**: 138건 → 양성의 5% 이상(약 300건). no_answer의 등급 어구 질문(현재 30건)도 같은 비율로.

**연결**: 09번 1-1절의 운영 원칙(등급은 UI에서 확정해 프롬프트에 넣지 않는다)은 그대로다. 이 변경은 고객이 말로 등급을 꺼낸 경우에 모델이 거절하지 않게 하는 보완이다.

#### 2-4. [필수] build 검사에 겹침 구간별 no_answer 비율을 넣는다

**무엇을**: `rebuild.py` build 검사(기존 `--gate-*` 옆)에 아래를 넣는다. 기존 규칙을 따라 미달이면 build를 실패로 기록하고 train으로 넘어가지 않는다. 기준 값이 None(미설정)이면 미달로 본다.

| 옵션(제안 이름) | 내용 | 제안 기본값 | 현재 rebuild 값 → 판정 |
| --- | --- | --- | --- |
| `--gate-max-low-overlap-na=<배수>` | 겹침 0.1 폭 구간 중 0.3 미만 구간마다: 구간 NA 비율 ≤ 배수 × 전체 NA 비율. 표본 30건 미만 구간은 판정 제외(출력은 함) | 1.5 | 0.1~0.2 44%, 0.2~0.3 27% (상한 15%) → **미달** |
| `--gate-min-low-overlap-pos=<비율>` | 겹침 0.2 미만 양성 / 전체 양성 하한 | 0.10 | 1.8% → **미달** |
| `--gate-min-pairs=<비율>` | 쌍이 있는 no_answer / 전체 no_answer 하한 (2-1) | 0.9 | 양쪽에 나오는 질문 11개 → **미달** |
| (보고만) | 30자 미만 질문 비율(양성·NA 각각), 등급 어구 + 공통 조항 양성 수, 구간별 표 전체 | — | 2.4% / 138건 |

- 구간별 표(구간·양성·NA·NA 비율)는 `stats.json`과 `logs/pipeline.log`에 모두 남긴다.
- **검사부터 구현하고, 현재 `data/finetune/rebuild/` 산출물에 돌려 미달이 나오는지 확인한다.** 이번 데이터를 통과시키는 검사라면 의미가 없다.
- 기존 `--gate-max-overlap-gap`은 남긴다. 그 docstring에 적힌 대로, 답이 든 발췌를 걷어내면 차이가 벌어진다. 그래서 이 검사를 맞추는 방법은 **양성을 늘리는 것(2-1·2-2)이 먼저**다. 낮은 겹침 no_answer를 버리는 것은 no_answer 분별(14~15/20)을 깎을 수 있어 마지막 수단이다.
- 조기 경고(선택): rewrite 단계 리포트에 "질문-gold 발췌 겹침 0.2 미만 양성 비율"을 찍는다. 방해 발췌 없이 계산되므로, build 전에 2-2가 모자란지 알 수 있다.

#### 3. 진행 순서 — 21시간을 다시 쓰지 않도록

지난 재구축 소요 시간(`data/faq/rebuild/logs/pipeline.log`): gen 6.96 + check 5.89 + rewrite 2.96 + build 0.99 + train 4.36 = **약 21.2시간**.

2-1과 2-4는 **build 단계만** 바꾼다. 기존 `data/faq/rebuild/rewrite/final`을 그대로 입력으로 쓸 수 있어서 gen·check·rewrite(약 15.8시간)를 다시 돌릴 필요가 없다.

| 단계 | 할 일 | 비용 |
| --- | --- | --- |
| 0 | **no_answer 라벨 확인(먼저)** — rebuild no_answer 200건 사람 표본 검수로 "방해 발췌에 답이 (일부라도) 있는" 비율을 잰다. 높으면 판정(`data/na_judge.py`) 방식을 고친 뒤 넘어간다. 틀린 라벨을 2-1 쌍으로 복제하면 지금보다 나빠진다 | 사람 검수 |
| A | 2-4 검사 구현 → 현재 rebuild 산출물에 돌려 **미달 확인** | 모델 없음 |
| B | 2-1 쌍 구성 구현 → 기존 final로 build만 다시(`--name`을 새로) → 검사 수치 확인 | build 약 1시간 |
| C | (선택) B 데이터로 train + answer_eval — 쌍 구성만의 효과를 따로 본다 | 약 4.4시간 + 평가 |
| D | 2-2·2-3 구현 → `run --from=rewrite` (gen·check 재사용) | rewrite 약 3시간 + build + train |
| E | answer_eval → 4번 기준으로 판정 → GGUF 변환 여부 결정 | |

C를 하면 쌍 구성(build)과 질문 추가(rewrite)의 효과가 섞이지 않는다. 비용은 학습 한 번이다.

#### 5. 하지 않는 것

- 심판 구조를 이번에 정리하지 않는다. 파이프라인의 심판은 네 겹이다 — 06 심판, 재작성 재심판, na_judge, na_judge 확인 검사.
  각각 이유가 있어 붙었지만 전체로 보면 층이 쌓였고, 그중 둘(na_judge와 확인 검사)은 같은 판정기·같은 캐시라 독립이 아니었다
  (자기가 거른 것을 자기가 검사해 "0건"이 나왔다 — docs/14 2-4절 "조용한 실패를 만들지 않는다"에 어긋난 경우).
  이번 재구축에서는 na_judge 기준을 질문 기준으로 바꾸고 확인 검사만 독립시킨다. 구조 정리는 이번 재구축 결과를 본 뒤에 한다 — 지금 바꾸면 효과 측정이 섞인다.

- 질문 재작성을 되돌리지 않는다(1절).
- 추론 프롬프트로 보정하지 않는다. 실험 A·B가 이미 실패했다(09번 1-1절).
- 평가 97문항을 학습·few-shot·재작성 예시에 쓰지 않는다.
- 낮은 겹침 no_answer를 버려서 검사를 맞추지 않는다(2-4, 마지막 수단).
