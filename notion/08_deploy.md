# 08 배포

코드를 저장소의 main 가지에 올리면(push) 운영에 들어가기까지 사람이 손대지 않는다. Jenkins가 이미지(프로그램과 실행 환경을 통째로 묶은 꾸러미)를 만들어 Harbor(사내 이미지 보관소)에 올리고, 인프라 저장소에 적힌 이미지 태그 한 줄을 바꿔 커밋한다. ArgoCD는 그 커밋을 읽어 클러스터의 앱을 새 이미지로 바꾼다. [docs:02_pipeline/14_deployment.md:106] 반영할 때마다 데이터베이스를 준비하는 초기화 작업도 함께 돌기 때문에, 데이터베이스 구조를 바꾸는 코드는 push 하나로 운영 데이터베이스까지 바뀐다. [docs:02_pipeline/14_deployment.md:335] 이 편은 무엇을 이미지에 담고 무엇을 빼는지, 이미지가 운영에 닿는 길, 그리고 그 길에서 사람이 문을 여닫는 자리를 다룬다. 클러스터 자체(노드, 진입점, 인증서)는 인프라 기술문서가 다룬다.

## 이미지에 담는 것과 담지 않는 것

이미지에는 FastAPI 서버와 React로 만든 화면 두 가지만 들어간다. 서버가 화면 파일까지 내주므로 Pod(함께 뜨고 함께 내려가는 프로그램 묶음) 하나로 서비스가 돈다. [docs:02_pipeline/14_deployment.md:27] 화면은 Node로 만들고 그 결과물만 Python 이미지로 옮겨 담는 두 단계 빌드를 써서, 빌드 도구가 최종 이미지에 남지 않는다. [docs:02_pipeline/14_deployment.md:38]

그래픽카드가 필요한 것은 이미지에 넣지 않는다. 클러스터는 한 물리 서버 위의 가상 머신들로 이루어져 그래픽카드가 가상 머신 안으로 들어오지 않는다. 그래픽카드를 가상 머신에 직접 넘기려면 호스트에서 드라이버를 떼어야 하고, 그러면 호스트에서 도는 Ollama를 포기해야 한다. [docs:02_pipeline/14_deployment.md:362] 검색을 그래픽카드 없이 Pod에서 돌리는 길도 있었지만, 리랭커가 후보를 질문과 하나씩 짝지어 비교하는 구조라 지연이 크게 늘어 전화를 받으며 쓰는 도구에 맞지 않았다. [docs:02_pipeline/14_deployment.md:436] 그래서 언어 모델, 검색 서버, 검색 데이터베이스는 모두 호스트에 두고 Pod는 네트워크로 부른다(→ 「모델 고르기와 서빙」). [docs:02_pipeline/14_deployment.md:364] 한 장의 그래픽카드에 모델 여럿을 올리는 배분을 쿠버네티스에 맡기기보다 직접 정하는 편이 지금은 다루기 쉽다는 판단도 있다. [docs:02_pipeline/14_deployment.md:366]

약관과 고객 데이터도 이미지에 넣지 않는다. 이미지는 Harbor를 거쳐 돌고, Jenkins가 빌드하려면 코드가 GitHub에 있어야 한다. 데이터를 이미지에 넣으면 그만큼 여러 곳에 복사되는데, 이 서비스는 모델과 데이터를 사내 서버에만 둔다는 원칙에서 출발했다. [docs:02_pipeline/14_deployment.md:372] 약관은 메리츠화재가 공개한 실제 상품 원문이고, 고객 원장에 든 10명은 여러 경우를 덮도록 만든 자료라 실제 고객은 아니다. 그래도 이름과 전화번호 모양을 하고 있어 git에서도 뺐고, 저장소에는 구조만 같은 예시 파일을 둔다. [docs:02_pipeline/09_ui_design.md:768] [docs:02_pipeline/14_deployment.md:378] 처음에는 약관 데이터를 git에 올려 이미지에 담았다. 크기(6.4MB)는 문제가 아니었지만 원칙에 어긋나 실행할 때 붙이는 방식으로 바꿨다. [docs:02_pipeline/14_deployment.md:431] 덕분에 git에 없는 약관 파일을 이미지에 복사하려다 빌드가 실패하는 문제도 함께 사라졌다. [docs:02_pipeline/14_deployment.md:376]

데이터는 호스트의 폴더를 사설망 안에서만 읽기 전용으로 나누어(NFS) Pod에 붙인다. 복사본이 없으므로 호스트에서 색인을 다시 만들어도 Pod가 보는 것과 어긋나지 않는다. [docs:02_pipeline/14_deployment.md:62] 붙여야 할 파일이 없거나 비어 있으면 서버는 빠진 파일을 모두 밝히고 기동을 멈춘다. 검색할 약관이 0건이어도 서버는 멀쩡히 뜨고 답도 하는데, 모델이 발췌 없이 답하므로 틀린 답을 자신 있게 하게 된다. 그 상태로 배포되면 누군가 로그를 보기 전까지 아무도 모른다. 조용히 틀리느니 시끄럽게 멈추는 쪽을 골랐다. [docs:02_pipeline/14_deployment.md:60] [docs:02_pipeline/14_deployment.md:392-394] 데이터베이스 접속 정보도 모두 환경변수로 받고, 없으면 이름을 밝히며 기동이 실패한다. [docs:02_pipeline/14_deployment.md:82]

## 이미지가 운영에 닿기까지

GitHub는 push를 받으면 웹훅(일이 생기면 상대에게 바로 알려 주는 호출)으로 Jenkins를 부른다. 웹훅을 놓쳐도 Jenkins는 15분마다 저장소를 살피는 폴링으로 잡는다. [docs:02_pipeline/14_deployment.md:151] 이미지 태그는 커밋 해시 앞 12자리다. `latest` 같은 이름을 쓰면 롤링 배포 중에 어느 Pod가 어떤 코드로 도는지 알 수 없게 되어 쓰지 않는다. [docs:02_pipeline/14_deployment.md:104]

앱 코드와 클러스터 설정(매니페스트)은 다른 저장소에 둔다. 한 저장소에 두면 Jenkins가 태그를 바꿔 push할 때마다 빌드가 다시 불려 끝없이 돈다. [docs:02_pipeline/14_deployment.md:102] 저장소를 나눈 뒤에도 같은 고리가 한 번 더 숨어 있었다. Jenkins의 폴링은 빌드 중에 받은 저장소까지 살피므로, 인프라 저장소를 Jenkins의 저장소 받기 단계로 받으면 태그 push가 다시 빌드를 불렀다. 그래서 인프라 저장소는 셸 명령으로 받는다. [docs:02_pipeline/14_deployment.md:443]

문서만 바뀐 push를 어떻게 다룰지도 정해야 했다. 문서는 이미지에 들어가지 않으므로 다시 구워도 같은 이미지에 새 태그만 붙는다. 그래서 바뀐 파일이 모두 문서, 검수 기록, 루트의 설명 파일이면 빌드는 돌되 성공으로 끝내고 이미지와 태그 단계만 건너뛴다. 빌드 자체를 부르지 않는 길도 있었겠지만, 그러면 push했는데 빌드가 없는 것이 고장인지 아닌지 가를 수 없다. 사람이 손으로 누른 빌드나 직전 성공 커밋을 못 찾을 때처럼 무엇이 바뀌었는지 모르면 언제나 빌드한다. [docs:02_pipeline/14_deployment.md:159]

ArgoCD는 이미지 보관소를 보지 않고 Git만 본다. 이미지는 각 노드가 Harbor에서 직접 당긴다. [docs:02_pipeline/14_deployment.md:108] 그래서 지금 무엇이 배포돼 있는지의 답이 늘 Git에 있다. 실제로 클러스터에서 손으로 Pod 수를 3으로 늘리자 ArgoCD가 곧바로 Git과 다르다고 잡았고, 반영하니 Git의 값 2로 돌아왔다(2026-10-16). [docs:02_pipeline/14_deployment.md:201] 열쇠는 역할마다 나눴다. Harbor에는 올리고 받는 Jenkins용 계정과 받기만 하는 노드용 계정을 따로 두어, 노드 쪽 열쇠가 새도 이미지를 덮어쓸 수 없다. [docs:02_pipeline/14_deployment.md:157] 인프라 저장소도 읽기 열쇠와 쓰기 열쇠를 따로 둔다. 처음에는 기한이 있는 토큰을 생각했으나, 토큰이 만료되면 배포가 조용히 멈추므로 기한 없는 열쇠 둘로 바꿨다. [docs:02_pipeline/14_deployment.md:422] Jenkins의 설정과 자격 증명도 화면에서 만들지 않고 인프라 저장소의 설정 파일로 남긴다. 화면에서 만들면 Jenkins를 다시 띄울 때 사라지고 무엇을 했는지 기록도 남지 않는다. [docs:02_pipeline/14_deployment.md:155]

## 자동 반영과 초기화 작업

ArgoCD는 처음에 사람이 반영(Sync) 단추를 누르게 두고, 설정이 뜻대로 들어가는지 눈으로 확인한 뒤 자동으로 바꿨다. [docs:02_pipeline/14_deployment.md:424] 자동이되 두 기능은 껐다. 하나는 클러스터를 Git과 다르게 바꾸면 되돌려 놓는 기능이고, 다른 하나는 Git에서 지운 것을 클러스터에서도 지우는 기능이다. 그래서 손으로 바꾼 것이 저절로 되돌아가지 않고, Git에서 지운 자원은 클러스터에 남는다. [docs:02_pipeline/14_deployment.md:333] 자동 반영을 끄고 켜는 스위치는 클러스터에서 사람이 누른다. [docs:02_pipeline/14_deployment.md:334] 네임스페이스(클러스터 안에서 한 서비스의 자원을 묶는 칸)도 ArgoCD가 소유하지 않게 사람이 만든다. 거기에 사람이 넣은 비밀값들이 있어, ArgoCD가 소유하면 정리 한 번에 함께 사라질 수 있다. [docs:02_pipeline/14_deployment.md:420]

반영할 때마다 초기화 작업이 먼저 돈다. 데이터베이스와 계정을 준비하고, 서비스 데이터베이스와 고객 원장의 구조 변경(마이그레이션)을 적용하고, 고객과 직원 표가 비어 있을 때만 시드 자료를 넣는다. 비어 있을 때만 넣으므로 여러 번 돌아도 결과가 같다. [docs:02_pipeline/14_deployment.md:237] 이것이 편한 만큼 위험도 있다. 마이그레이션이 든 코드는 push만으로 운영 데이터베이스에 적용되고, 이미지를 옛 판으로 되돌려도 데이터베이스 구조는 돌아오지 않는다. 마이그레이션은 더하기만 하므로 옛 이미지가 새 구조 위에서 뜬다. [docs:02_pipeline/14_deployment.md:335] [docs:02_pipeline/14_deployment.md:455] 그래서 사람이 지켜봐야 하는 구조 변경이나 데이터베이스 복구는 자동 반영을 먼저 끄고 넣은 뒤 다시 켠다. [docs:02_pipeline/14_deployment.md:338] 공개 주소를 내는 터널만은 자동으로 두지 않고 사람이 반영한다. 터널이 깨지면 서비스뿐 아니라 고칠 도구와 볼 도구까지 함께 안 보이기 때문이다(→ 「로그인, 체험 계정, 터널」). [docs:02_pipeline/14_deployment.md:337]

## 운영 플래그

검색과 코드 답의 여러 기능은 코드의 기본값을 바꾸지 않고 운영 설정 파일(ConfigMap)에서만 켠다. 문제가 생기면 그 설정 한 줄만 되돌리면 된다. [docs:02_pipeline/14_deployment.md:231] 새 검색 색인으로 바꾸는 것처럼 코드와 설정이 함께 바뀔 때는 앱을 먼저 올리고 설정을 나중에 올린다. 거꾸로 하면 옛 이미지가 새 약관 파일을 읽으면서 검색은 옛 색인으로 해, 찾은 결과와 약관 파일이 어긋난다. [docs:02_pipeline/14_deployment.md:233] 설정만 바뀌는 경우에는 반영 뒤 앱을 다시 띄워야 새 값이 들어간다. 약관을 새로 만들었을 때도 같다. 서버가 뜰 때 약관을 메모리에 올리기 때문이다. [docs:02_pipeline/14_deployment.md:239] [docs:02_pipeline/14_deployment.md:64] 평가 때 날짜를 고정하는 설정은 운영에 넣지 않고, 운영은 실제 날짜를 쓴다. [docs:02_pipeline/14_deployment.md:241]

기능을 켠 뒤 잘 도는지는 클러스터 안에서 도는 집계 명령으로 본다. 모드별 턴 수, 코드 답 규칙별 발동 수, 모델이 거절한 비율, 좋아요와 싫어요 수 같은 숫자만 내고 질문과 답의 글, 상담원, 고객 값은 어떤 옵션으로도 내지 않는다(→ 「코드가 답하는 질문」). [docs:02_pipeline/14_deployment.md:243] [docs:02_pipeline/14_deployment.md:250]

## 클러스터에서 도는 모습

앱은 Pod 두 개로 돌고 둘은 반드시 다른 노드에 놓인다. 정비로 노드를 비울 때도 최소 하나는 남긴다. [docs:02_pipeline/14_deployment.md:316] 앱이 놓일 수 있는 노드가 둘뿐이라, 새 판으로 바꿀 때는 옛 Pod 하나를 먼저 내리고 그 자리에 새 Pod를 띄운다. 그동안은 남은 Pod 하나가 요청을 받는다. 이렇게 바꾼 뒤 재시작은 23초 걸렸고, 1초 간격으로 찌른 점검은 한 번도 실패하지 않았다(2026-11-10). [docs:02_pipeline/14_deployment.md:322] 빌드와 배포 도구는 앱과 다른 노드에 있어, 그 노드가 죽어도 상담은 돈다. [docs:02_pipeline/14_deployment.md:324]

MySQL은 클러스터 안에서 돌고 복제본(Replica)을 하나 더 둔다. 자동으로 넘어가는 장치는 없고 원본이 죽으면 사람이 복제본을 원본으로 올린다. 자동 전환에는 그 일을 맡는 운영 프로그램이 필요한데 자원이 모자라 이 방식을 골랐다. 복제본은 백업이 아니라서 지운 것은 복제본에서도 지워진다. [docs:02_pipeline/14_deployment.md:323] [docs:02_pipeline/14_deployment.md:457] 고객 원장은 서비스 데이터베이스와 따로 두고 읽기만 하는 계정으로 읽는다. 실무에서 고객 데이터는 보험사 기간계에 있고 이 서비스는 그것을 빌려 읽는 쪽이라, 복사해 두면 원본이 바뀌어도 따라가지 못하기 때문이다(→ 「대화 기록과 관리자 화면」). [docs:02_pipeline/14_deployment.md:382-386]

## 알려진 한계

- 개발, 시험, 운영 환경을 나누지 않았다. 개발은 로컬에서 하고 클러스터는 운영 하나뿐이다. 한 대의 서버에 환경을 여럿 올리기에는 자원이 모자란다 [docs:02_pipeline/14_deployment.md:450]
- 데이터베이스 구조 변경은 되돌아가지 않는다. 설정은 ArgoCD가 Git대로 되돌리지만 구조는 아니다. 되돌릴 수 없게 깨는 변경이 생기면 그때 방법을 정한다 [docs:02_pipeline/14_deployment.md:455]
- MySQL은 자동으로 넘어가지 않는다. 원본이 죽으면 사람이 알아채고 복제본을 올리기까지 서비스가 멈춘다. 앱 요청까지 옮기는 전환은 아직 해 보지 않았다 [docs:02_pipeline/14_deployment.md:457]
- 검색 데이터베이스(Milvus)는 아직 호스트의 컨테이너로 돈다. 클러스터로 옮길 수 있지만 따라붙는 부속이 자원을 더 먹는다 [docs:02_pipeline/14_deployment.md:453]
- 이미지 크기의 큰 몫이 검색 데이터베이스 라이브러리다. 평가와 서비스가 같은 코드를 쓰게 하려고 그대로 두었다 [docs:02_pipeline/14_deployment.md:434] [docs:02_pipeline/14_deployment.md:454]
- 호스트 서비스의 기동 순서를 실제 재부팅으로 시험하지 않은 일과 호스트, 공용 검색 모델 서버, 물리 서버 한 대에 걸린 한계와 조건은 → 「알려진 한계」 한 편에 모았다.

## 용어 풀이

- 이미지: 프로그램과 실행 환경을 통째로 묶은 꾸러미. 클러스터는 이것을 받아 Pod로 띄운다
- 태그: 이미지에 붙이는 이름표. 여기서는 커밋 해시 앞 12자리 [docs:02_pipeline/14_deployment.md:150]
- Pod: 쿠버네티스에서 함께 뜨고 함께 내려가는 프로그램 묶음
- 매니페스트: 클러스터에 무엇을 어떻게 띄울지 적은 설정 파일
- Sync(반영): ArgoCD가 Git에 적힌 상태대로 클러스터를 맞추는 일
- 마이그레이션: 데이터베이스 구조를 바꾸는 단계. 한 번 적용하면 되돌리지 않는다
- 초기화 작업: 반영할 때마다 앱보다 먼저 돌아 데이터베이스 구조와 시드 자료를 맞추는 일회성 작업
- ConfigMap: 클러스터에 두는 설정 값 묶음. 코드를 다시 빌드하지 않고 기능을 켜고 끈다
- 롤링 배포: Pod를 하나씩 차례로 새 판으로 바꾸는 배포
- 웹훅: 일이 생기면 상대에게 바로 알려 주는 호출
- 복제본(Replica): 원본 데이터베이스의 변경을 그대로 따라 쓰는 사본
- NFS: 한 컴퓨터의 폴더를 네트워크로 다른 컴퓨터에 나눠 주는 방식
