# 03-01 모델 고르기와 서빙

이 편은 답을 쓰는 언어 모델을 어떻게 골랐는지, 그 모델과 검색 모델들을 서버에 어떻게 올려 두었는지를 다룬다. 고른 모델은 한국어 언어 모델 Tri-7B이고, 서버의 그래픽카드 한 장 위에서 Ollama(언어 모델을 내려받아 돌려 주는 실행 도구)가 돌린다. 검색에 쓰는 임베딩 모델과 리랭커는 같은 그래픽카드를 나눠 쓰는 별도 모델 서버에 있다. [docs:02_pipeline/00_model_setup.md:9] [docs:02_pipeline/09_ui_design.md:537]

## 네 관문으로 후보를 좁혔다

후보는 네 관문을 차례로 거쳤다. 첫째, 상업 배포가 되는 라이선스여야 한다. 사내 서비스로 쓰려면 빠질 수 없는 조건이다. 둘째, 가진 그래픽카드(RTX 5070 Ti, 그래픽 메모리 16GB) 한 장으로 답을 쓰는 일과 학습을 모두 돌려야 하므로, QLoRA(모델을 줄여 올린 채 덧붙인 작은 층만 가르치는 학습 방식)로 그 메모리 안에서 가르칠 수 있는 크기여야 한다. 셋째, Ollama가 읽는 파일 형식으로 바꿀 수 있는 구조여야 한다. 넷째, 이 셋을 통과한 후보끼리 한국어 대화 점수와 한국어 지식 시험 점수(KMMLU)를 견준다. [docs:02_pipeline/00_model_setup.md:38-43]

첫 관문에서 EXAONE 3.5가 빠졌다. 라이선스에 상업 배포를 막는 조항이 있었다. Qwen 2.5 7B는 한국어 대화 점수가 뒤졌고, 학습 데이터를 만들 때 답에 중국어가 섞이는 일도 보였다. [docs:02_pipeline/00_model_setup.md:47] [docs:02_pipeline/00_model_setup.md:50] 마지막에 남은 것은 Kanana 1.5 8B와 Tri-7B였다. 둘 다 Apache 2.0 라이선스이고 크기도 비슷했는데, 모델 카드에 공개된 KMMLU가 Tri-7B 53.51, Kanana 48.28로 Tri-7B가 5점쯤 높아 Tri-7B를 골랐다. [docs:02_pipeline/00_model_setup.md:48-49] [docs:02_pipeline/00_model_setup.md:52] Tri-7B는 Trillion Labs가 만든 77억 6천만 매개변수 모델이다. [docs:02_pipeline/00_model_setup.md:17]

여기서 떨어진 Kanana는 나중에 다른 자리로 돌아왔다. 학습 데이터를 거를 심판 모델을 고를 때다. 심판은 생성 모델과 달라야 했으므로, Tri-7B가 아닌 후보로 Kanana가 다시 시험대에 올랐다. 그 시험에서 한국어 지식 점수가 높은 모델이 판정도 잘하지는 않는다는 것이 드러났다(→ 「학습 데이터 거르기: 검사와 심판」). [docs:02_pipeline/00_model_setup.md:56-60]

## 원본은 약관을 모른다

Ollama에 올린 원본 Tri-7B는 한국어로 막힘없이 답했고, 답이 나오는 데 1.8~3.0초가 걸렸다(두 번 잼, 2026-09-29~2026-10-13 사이). [docs:02_pipeline/00_model_setup.md:110] 그런데 "보험금 청구 서류를 낸 뒤 얼마나 빨리 받나요?"라고 물으면 펫퍼민트 약관의 지급 기일이 아니라 "1~2주일" 같은 흔한 보험 상식으로 답했다. [docs:02_pipeline/00_model_setup.md:112] 말을 못하는 것이 아니라 이 약관을 모르는 것이다. 이것이 약관을 찾아 읽히는 검색과, 약관으로 따로 가르치는 학습이 둘 다 필요하다는 첫 근거가 되었다. [docs:02_pipeline/00_model_setup.md:114]

## Ollama에 올리기까지

공개 저장소에서 받은 원본은 Ollama가 바로 읽지 못하는 형식이라, llama.cpp 도구로 GGUF(Ollama가 읽는 모델 파일 형식)로 바꿨다. [docs:02_pipeline/00_model_setup.md:64] 바꾼 파일은 15.1GB였다. 이대로는 16GB 그래픽카드에 다른 것이 들어갈 자리가 거의 없어, Q4_K_M 방식으로 양자화(모델의 숫자를 더 적은 비트로 줄여 담는 일)해 4.4GB로 줄였다(2026-09-29까지). [docs:02_pipeline/00_model_setup.md:66]

앞서 EXAONE을 다룰 때는 변환과 양자화에서 모두 손을 대야 했다. EXAONE은 구조가 특이해 변환에 덧붙인 수정이 필요했고, 설정 키 이름이 표준과 달라 양자화할 때도 키를 직접 지정해야 했다. Tri-7B는 표준 llama 구조를 따르므로 그런 우회가 필요 없으리라고 먼저 짐작하고, 그 짐작을 시험하는 순서로 갔다. 실제로 변환은 한 번에 됐고, 양자화도 따로 지정하지 않고 그대로 됐다(14,357MB에서 4,411MB, 2026-09-29까지). [docs:02_pipeline/00_model_setup.md:76] [docs:02_pipeline/00_model_setup.md:80-82]

막힌 곳은 엉뚱한 데 있었다. Ollama는 도커 컨테이너(프로그램을 격리된 칸 안에서 돌리는 꾸러미) 안에서 도는데, 모델 등록 설정에 호스트의 파일 경로를 그대로 적었더니 등록이 "모델 이름이 잘못됐다"는 오류로 실패했다. 컨테이너 안에서는 호스트의 경로가 보이지 않기 때문이었다. 모델 파일과 설정을 컨테이너 안으로 복사하고 경로도 컨테이너 안쪽으로 고쳐 적어 등록했다. [docs:02_pipeline/00_model_setup.md:87-89]

서빙 도구로 vLLM 대신 Ollama를 고른 것은 지금의 쓰임새 때문이다. vLLM의 강점은 많은 사람이 동시에 물을 때 요청을 묶어 빠르게 처리하는 데 있는데, 지금은 한 사람이 만들고 실험하는 단계라 그 강점이 아직 필요 없다. Ollama는 GGUF를 바로 읽고 모델을 바꿔 가며 실험하기 쉬웠다. [docs:02_pipeline/00_model_setup.md:68]

## 그래픽카드 한 장을 나눠 쓴다

앱 서버는 쿠버네티스 클러스터에서 도는데, 그 클러스터는 호스트 위의 가상 머신들로 만들어져 있어 그래픽카드가 가상 머신 안으로 들어가지 않는다. 그래픽카드를 가상 머신에 통째로 넘기려면 호스트에서 드라이버를 떼어 내야 하고, 그러면 호스트의 Ollama를 포기해야 한다. 그래서 그래픽카드를 쓰는 것은 모두 호스트에 두고, 클러스터의 앱은 네트워크로 부른다. [docs:02_pipeline/14_deployment.md:362-364] 검색을 그래픽카드 없이 돌리는 길도 있었지만, 리랭커는 후보를 질문과 한 쌍씩 맞대어 읽는 구조라 느려진다. 전화를 받으며 쓰는 도구에는 맞지 않아 버렸다. [docs:02_pipeline/09_ui_design.md:550]

16GB 한 장에 모델 넷이 함께 오른다. 임베딩 모델 KURE-v1(2.12GB)과 리랭커 bge-reranker-v2-m3(1.06GB)는 늘 올라가 있고(2026-11-11), Ollama 쪽은 원본 Tri-7B와 약관으로 가르친 판을 필요할 때 갈아 끼운다. [docs:02_pipeline/09_ui_design.md:562-567] 검색 모델 둘이 차지하는 몫을 재 보니 막 띄웠을 때 3,498MiB, 검색을 돌린 뒤 6,408MiB였다(2026-11-11). 늘어난 몫은 추론하며 쌓이는 캐시다. [docs:02_pipeline/09_ui_design.md:571] 쿠버네티스의 그래픽카드 배분 기능은 기본으로 카드를 통째로 한 곳에 주므로, Ollama와 검색이 둘 다 필요한 이 구조에서는 메모리 배분을 직접 관리하는 쪽이 지금은 다루기 쉽다. [docs:02_pipeline/14_deployment.md:366]

이 좁은 메모리가 기능을 정하기도 했다. 원본과 학습한 판은 하나가 8.7GB쯤이라 검색 모델과 함께 둘이 동시에 오르지 못한다. 업무특화 모드에서 이어지는 질문을 원본 모델로 다시 써서 검색하게 하면 턴마다 모델을 갈아 끼우느라 5초쯤 늦어졌다(2026-10-21). 그래서 업무특화 모드는 모델로 질문을 다시 쓰지 않고, 앞 질문에 이어 붙여 검색한다. [docs:02_pipeline/09_ui_design.md:277]

검색 모델 둘은 이 서비스만 쓰지 않는다. 같은 호스트에서 도는 다른 프로젝트의 챗봇도 같은 모델을 쓰므로, 두 모델을 공용 모델 서버로 떼어 냈다. 모델은 그대로이고 도는 자리만 바뀌었다. 모델 판은 내려받아 둔 것으로 고정하고, 서버가 바깥에서 새 판을 받지 않게 했다. [docs:02_pipeline/14_deployment.md:342] [docs:02_pipeline/14_deployment.md:346] 그 뒤 호스트의 검색 서버는 키워드 검색과 벡터 조회, 정렬만 하고 그래픽카드를 쓰지 않는다. 모델 서버 주소를 주지 않으면 예전처럼 제 안에 모델을 올리므로, 노트북이나 오프라인 스크립트에서도 같은 코드가 돈다. [docs:02_pipeline/14_deployment.md:347]

## 학습한 모델을 바꿔 끼우는 법

약관으로 가르친 결과는 원본에 덧붙이는 작은 층(어댑터)이다. 이것을 운영에 올리려면 호스트에서 원본과 합치고, GGUF로 바꾸고, 양자화해 Ollama에 새 이름으로 등록한다. [docs:02_pipeline/10_consultation_flow.md:165] 양자화는 원본과 같은 Q4_K_M으로 맞춘다. 둘이 다르면 모드 사이의 답 차이가 학습 덕인지 양자화 차이인지 가를 수 없기 때문이다. [docs:02_pipeline/09_ui_design.md:580-582]

앱 서버에는 모델이 없고 "어느 이름의 모델을 부를지"만 설정으로 들고 있다. 그래서 모델을 바꿀 때 이미지를 다시 만들 필요가 없다. 설정값 하나를 새 이름으로 바꾸고 서버를 다시 띄우면 된다. [docs:02_pipeline/10_consultation_flow.md:161] [docs:02_pipeline/10_consultation_flow.md:166] 모델 이름에는 판 번호를 박고 "최신" 같은 이름을 쓰지 않는다. 서버를 하나씩 바꾸는 동안 어느 서버가 어느 모델을 부르는지 알 수 없게 되기 때문이다. [docs:02_pipeline/10_consultation_flow.md:168] 새 모델을 등록해도 옛 모델은 Ollama에 그대로 남아 있어, 바꾸는 동안 옛 서버와 새 서버가 둘 다 답할 수 있고, 문제가 생기면 설정만 되돌린다. [docs:02_pipeline/10_consultation_flow.md:170] 지금 운영의 업무특화 모드는 rebuild4라는 이름의 판을 쓴다(→ 「파인튜닝과 거절 문제」). [docs:02_pipeline/07_finetuning.md:5]

## 껐다 켜도 다시 뜨게

한 번은 서버를 재부팅했더니 Ollama와 검색 데이터베이스 Milvus 컨테이너가 올라오지 않았다. 컨테이너를 띄울 때 재시작 정책을 주지 않아 기본값인 "다시 띄우지 않음"이었다. 지금은 "일부러 멈춘 것이 아니면 다시 띄움"으로 두었다. "언제나 다시 띄움"을 고르지 않은 것은, 사람이 일부러 멈춘 컨테이너는 재부팅 뒤에도 꺼진 채로 두는 편이 자연스럽기 때문이다. [docs:02_pipeline/00_model_setup.md:93-95] 그때 Milvus는 안에 품은 설정 저장소(etcd)가 망가져 뜨지 못했다. 데이터를 비우고 다시 색인해 살렸고, 지금은 그 저장소를 따로 띄워 준비된 것을 확인한 뒤 Milvus가 뜬다. [docs:02_pipeline/00_model_setup.md:97]

공용 모델 서버를 떼어 내면서 호스트가 켜질 때의 순서가 한 단계 늘었다. 모델 서버가 먼저 떠서 모델을 다 올린 것을 확인하고, 그다음 Milvus를 기다린 뒤 검색 서버가 뜬다. 검색 서버는 모델 서버를 기다리기만 하고 거기에 매여 있지는 않아서, 모델 서버를 다시 띄워도 함께 내려가지 않는다. [docs:02_pipeline/14_deployment.md:352-354]

## 알려진 한계

- 동시에 많은 상담원이 묻는 상황에 맞춘 서빙(vLLM)으로 가지 않았다. 지금은 한 사람이 만들고 실험하는 단계라 그 강점이 필요 없고, 상담원 여럿이 동시에 쓰게 되면 그때 다시 본다. [docs:02_pipeline/00_model_setup.md:104]
- 공용 모델 서버를 떼어 낸 뒤의 켜지는 순서를 실제 재부팅으로 시험하지 않은 일, 그래픽카드 한 장에서 오는 조건, 서비스 전체에 걸린 한계는 → 「알려진 한계」 한 편에 모았다.

## 용어 풀이

- Ollama: 언어 모델 파일을 올려 두고, 다른 프로그램이 부르면 답을 써 돌려주는 실행 도구
- GGUF: Ollama와 llama.cpp가 읽는 모델 파일 형식
- 양자화: 모델 안의 숫자를 더 적은 비트로 줄여 담아 파일과 메모리를 줄이는 일. Q4_K_M은 그 방식 가운데 하나다
- QLoRA: 모델을 줄여 올린 채, 덧붙인 작은 층만 가르치는 학습 방식. 그래픽 메모리가 적어도 큰 모델을 가르칠 수 있다
- 어댑터: QLoRA로 가르친 결과인 작은 층. 원본과 합쳐야 Ollama에 올릴 수 있다
- KMMLU: 여러 분야의 한국어 지식을 묻는 시험 문제로 언어 모델을 재는 점수
- 그래픽 메모리(VRAM): 그래픽카드에 달린 메모리. 모델이 돌려면 여기에 올라가야 한다
- 공용 모델 서버: 임베딩 모델과 리랭커를 올려 두고 여러 프로젝트가 함께 부르는 호스트의 서버
