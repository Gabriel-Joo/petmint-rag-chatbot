# 운영과 모니터링

> 이 글은 펫퍼민트 사이트가 어디에 어떻게 떠 있는지, 그리고 잘 돌고 있는지를 무엇으로 지켜보는지를 보여 드립니다.

**펫퍼민트는 직접 세운 쿠버네티스 클러스터에서 앱 두 벌이 서로 다른 노드에 떠 있고, 그래픽카드를 쓰는 언어 모델과 검색은 클러스터 밖의 서버 한 대에서 돕니다. 서비스가 떠 있는지, 답이 얼마나 걸리는지, 오류와 거절이 얼마나 나는지는 Grafana 대시보드 「petmint 운영」 한 장에서 봅니다.** [docs:02_pipeline/14_deployment.md:316] [docs:02_pipeline/14_deployment.md:461] [docs:02_pipeline/15_monitoring.md:28]

![Grafana의 「petmint 운영」 대시보드 30일 화면. 맨 위 줄에 응답 가능한 서버 수 2와 최근 24시간 재시작 0, 초당 접속 요청량, 서버 오류 비율이 있고, 그 아래로 모드별, 시간대별 질문 수, 확인 불가 응답 비율, 답변 실패와 중단 비율, 규칙별 코드 답 수, 답한 방식, 상담원 평가, 답변과 조항 검색에 걸린 시간, 그래픽카드 사용률과 메모리, 올라간 AI 모델이 이어집니다. 서버 기록 칸이 있는 맨 아래 줄은 접속 주소가 보여 잘라 냈습니다. 인프라 저장소에서 08_grafana_petmint.png로 찍은 사진을 옮겨 왔습니다](img/08_ops_grafana.png)

## 사이트가 떠 있는 모습

화면과 서버를 묶은 앱은 클러스터에서 두 벌이 돌고, 둘은 반드시 다른 노드에 놓입니다. 정비로 노드 하나를 비울 때도 적어도 한 벌은 남깁니다. [docs:02_pipeline/14_deployment.md:316] 새 판으로 바꿀 때는 옛 앱 하나를 먼저 내리고 그 자리에 새 앱을 띄우며, 그동안 남은 한 벌이 요청을 받습니다. 이렇게 바꾼 뒤 재시작은 23초 걸렸고, 1초마다 찌른 점검은 한 번도 실패하지 않았습니다(2026-11-10). [docs:02_pipeline/14_deployment.md:322] 상담 기록이 쌓이는 MySQL도 클러스터 안에 있고, 복제본을 하나 더 둡니다. [docs:02_pipeline/14_deployment.md:323]

서버는 바깥으로 포트를 하나도 열지 않습니다. Cloudflare 터널이 먼저 바깥으로 연결을 걸어 두고, 방문자의 요청은 그 연결을 타고 들어옵니다. [docs:02_pipeline/13_access_and_tunnel.md:34] 답을 쓰는 언어 모델, 약관 조각을 담은 검색 데이터베이스, 검색 서버는 그래픽카드가 있는 서버 한 대에 모여 있습니다. [docs:02_pipeline/14_deployment.md:461] 코드를 저장소에 올리면 Jenkins가 이미지를 만들고 ArgoCD가 클러스터에 반영해, 사람이 손대지 않고 운영에 들어갑니다(→ 「한눈에 보는 펫퍼민트」). [docs:02_pipeline/14_deployment.md:91-97] 빌드와 배포 도구, 모니터링은 앱과 다른 노드에 두어 그 노드가 죽어도 상담은 돕니다. [docs:02_pipeline/14_deployment.md:324]

## 무엇을 보나

대시보드는 서비스 상태와 접속량, 질문량, 답변 품질과 속도, AI 서버의 네 묶음이고, 열면 지난 30일을 보여 줍니다. [docs:02_pipeline/15_monitoring.md:28] 칸 이름과 마우스를 올리면 뜨는 설명은 개발자가 아닌 사람이 읽는다고 보고 고쳐 썼습니다. 이름은 무엇을 세는지를, 설명은 값이 높거나 낮으면 무슨 뜻인지를 말합니다. [docs:02_pipeline/15_monitoring.md:30]

서비스가 떠 있는지는 맨 위 줄에서 봅니다. 응답할 수 있는 앱 서버 수가 정상이면 2이고, 그 옆에 최근 24시간 동안 앱이 다시 시작된 횟수가 있습니다. [docs:02_pipeline/15_monitoring.md:28] 그래픽카드 서버 쪽은 검색 데이터베이스가 살아 있는지와, 언어 모델 서버에 지금 어느 모델이 올라와 있는지를 봅니다. 모델 목록까지 보는 것은 그래픽카드 한 장에 여러 모델이 번갈아 올라가, 어느 모델이 올라와 있는지가 답이 늦어진 까닭을 가늠하는 단서가 되기 때문입니다. [docs:02_pipeline/15_monitoring.md:33] [docs:02_pipeline/14_deployment.md:366]

답이 얼마나 걸리는지는 하루마다 두 값으로 봅니다. 「보통」은 그날 질문의 절반이 이보다 빨랐던 값이고, 「느린 편」은 열 번 중 아홉 번이 이보다 빨랐던 값입니다. [docs:02_pipeline/15_monitoring.md:28] 답을 다 쓰기까지의 시간, 첫 글자가 나오기까지의 시간, 그 가운데 조항 검색을 기다린 시간을 따로 남겨, 답이 늦을 때 어디서 늦었는지 가를 수 있습니다. [docs:02_pipeline/12_data_storage.md:58-59]

오류는 세 겹으로 봅니다. 클러스터 입구에서 본 서버 오류 비율, 답을 만들다 실패하거나 중간에 멈춘 질문의 비율, 그리고 모델이 "확인되지 않는다"며 답을 내지 않은 확인 불가 응답의 비율입니다. [docs:02_pipeline/15_monitoring.md:26] [docs:02_pipeline/15_monitoring.md:28] 확인 불가 응답은 모델 평가에서 쓰는 것과 같은 판정으로 세어, 평가 때 잰 값과 운영에서 보는 값을 같은 잣대로 견줄 수 있습니다. [docs:02_pipeline/15_monitoring.md:31]

지표는 클러스터 입구와 노드, 그래픽카드 서버의 수집기에서 Prometheus로 모여 15일 쌓이고, 질문과 답에 관한 숫자는 앱이 질문마다 남기는 기록을 Grafana가 데이터베이스 복제본에서 바로 읽어 셉니다. [docs:02_pipeline/15_monitoring.md:25-26] [docs:02_pipeline/14_deployment.md:325]

## 질문 글은 읽지 않고 셉니다

대시보드는 상담원이 입력한 질문과 답의 글을 꺼내지 않습니다. Grafana가 데이터베이스를 읽는 계정은 분류와 시간과 상태 칸만 읽을 수 있고, 질문과 답, 의견 칸에는 권한이 없어 읽으려 하면 권한 오류가 납니다. [docs:02_pipeline/15_monitoring.md:27] 숫자가 이상해 하나하나를 봐야 할 때는 관리자 화면에서 그 상담을 찾아 읽습니다. 대시보드는 전체 흐름을, 관리자 화면은 한 건 한 건을 맡도록 나눴습니다(→ 「관리자 화면」). [docs:02_pipeline/13_access_and_tunnel.md:154]

## 아직 보지 않는 것

알림이 없습니다. 무엇을 누구에게 알릴지 아직 정하지 않아서, 지금은 보는 데까지만 했습니다. 그래서 이상이 생기면 누군가 대시보드를 열어야 보입니다. [docs:02_pipeline/15_monitoring.md:9] [docs:02_pipeline/15_monitoring.md:111]

앱 서버에는 아직 지표를 내주는 창구가 없습니다. 그래서 요청마다 걸린 시간과 동시에 이어진 대화 수는 앱이 직접 내지 못하고, 클러스터 입구의 지표와 질문마다 남긴 기록으로 미루어 봅니다. [docs:02_pipeline/15_monitoring.md:26] 그래픽카드 서버의 검색 서버와, 문장을 벡터로 바꾸는 공용 모델 서버도 살아 있는지를 따로 보지 않습니다. 모델 서버가 죽으면 검색 서버의 점검도 실패하므로 간접으로만 보입니다. [docs:02_pipeline/15_monitoring.md:68-69]

## 무엇이 어려웠나

사내규정 모드에서 정년을 바르게 답한 질문이 확인 불가 응답으로 찍혔습니다. 걸린 것은 답 끝에 붙는 "인사부서에 확인하라"는 맺음말이었습니다. [docs:02_pipeline/15_monitoring.md:100] 판정을 고쳐 맺음말은 다른 답 없이 그것뿐일 때만 거절로 치게 했고, 바꾸기 전에 운영 기록 85건으로 재어 거절이 22건에서 18건으로 줄고 빠진 넷이 모두 잘못 찍혔던 것임을 확인했습니다(2026-11-11~12). [docs:02_pipeline/15_monitoring.md:78-80] [docs:02_pipeline/15_monitoring.md:103]

칸 이름을 고쳐 쓰다 빈 곳도 찾았습니다. 답을 만들다 실패한 질문이 대시보드 어디에도 보이지 않아, 답변 실패와 중단 비율 칸을 더했습니다. [docs:02_pipeline/15_monitoring.md:30] 대시보드를 화면에서 만들면 Grafana가 다시 뜰 때 사라져서, 설정 파일로 넣어 뜰 때마다 다시 읽게 했습니다. [docs:02_pipeline/15_monitoring.md:29]

여러 화면에 걸친 한계는 → 「알려진 한계」에 모았습니다. 무엇을 어떻게 재는지는 기술문서 [「모니터링」](../notion/09_monitoring.md), 이미지가 운영에 닿는 길은 [「배포」](../notion/08_deploy.md)에 있습니다.
